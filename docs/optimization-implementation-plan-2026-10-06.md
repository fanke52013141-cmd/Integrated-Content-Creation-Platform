# 心流公众号创作项目：详细优化实施方案

日期：2026-10-06。依据：`user-journey-review-2026-10-06.md` 及当前工作区代码。

本文为待实施方案，接口、字段和文件拆分均是建议，不表示已经实现。沿用审查报告 F01—F12 编号。目标是把缺陷转成可开发、可验收、可回退的任务，并补齐真实作者从开始写作到交付后的操作。

## 1. 产品目标与实施原则

最终必须顺畅支持三条路径：

1. **已有文章，无 AI 配置**：导入 Markdown/文字 → 导入自己的封面及正文图 → 编辑 → 排版 → 导出；无需先完成账号定位或 AI 方案。
2. **从零创作，有 AI 配置**：选择主题/热点 → 选择是否使用账号定位 → 收集资料 → 确认框架 → 生成正文 → 人工修改/可选评审 → 配图 → 排版 → 交付。
3. **继续旧文章**：搜索或首页直达 → 恢复未保存内容 → 修改或重试任务 → 保持文章、版本和图片上下文一致 → 核对交付结果。

实施约束：

- 保留 SQLite、本地草稿、版本历史、IPC 白名单、密钥加密、发布预检与恢复回退机制。
- 修复集中在实际问题边界；不先整体重写数据库，不先更换编辑器，不先搭建复杂任务平台。
- 用户意图、执行参数、执行结果必须分开表达。数量不能决定写入位置，HTTP 成功不能代表正文完成，提交请求不能代表远端收到。
- 业务判断在主进程执行。渲染层负责展示和输入，按钮禁用不能替代服务端检查。
- 所有影响正文、图片和交付状态的操作绑定文章 ID、版本 ID 或记录 ID。按标题寻找对象只用于搜索，不用于写入。

## 2. 实施批次与依赖

| 批次 | 内容 | 交付出口 |
| --- | --- | --- |
| A：恢复核心可靠性 | F01 配置保存、F02 改稿语义、F03 输出完整性；修复现有冒烟脚本 | 新用户能接入模型；失败和重试不会误改原稿；生成结果状态可信 |
| B：完成创作与交付闭环 | F05 手动配图、F04 图片交付、F06/F07 查询选择、F08 推送核对 | 无 AI 流程可走通；旧文章可直达；图片与异常交付可处理 |
| C：提高写作效率 | F09 页面布局、账号/选题/热点/框架交接、生成进度反馈 | 用户能看懂当前作品、下一步以及实际使用的账号与资料 |
| D：内容依据与数据保障 | F11 可携带备份、F12 长素材、F10 证据评审、复盘指标 | 数据可带走；素材使用范围透明；事实意见有出处 |

依赖顺序：F02 的写入策略先于 F03 的结果采纳；F05 提供真实图片场景后验收 F04；F06/F07 先于页面查询抽取；F12 的片段与出处模型先于 F10 的证据关联。F11 可在数据迁移机制就绪后提前实施，无需等内容质量功能结束。

不按“全部前端 → 全部后端 → 最后测试”分工序。每个任务都交付一条完整、可回归的行为。

## 3. F01：AI 配置保存与验证统一

### 用户应看到的行为

- 点击“测试并保存”后，依次显示“正在测试连接”“正在保存”，最终显示“已保存，默认文本模型连接正常”。
- 保存成功后，配置保持选中、密钥输入清空、不弹弃改确认；新建表单转成编辑已有配置。
- 用户主动切换配置且存在真实未保存修改时，才出现弃改确认。
- 修改显示名称不影响连接验证；修改地址、密钥或被验证模型时，该范围的验证失效。
- 文本模型测试通过，不代表图片生成等能力也已验证。卡片注明验证范围。

### 具体开发任务

1. 在 `ProvidersPage.tsx` 提取纯表单加载函数 `loadProviderIntoForm(provider)`，统一设置 form、selectedId、baseline 和密钥空值。
2. `chooseProvider` 只处理用户切换；保存成功直接调用加载函数，禁止再走弃改检查。
3. 表单脏状态采用标准化后的持久字段比较，排除 loading、临时测试提示等 UI 状态。
4. 提交时捕获不可变配置快照；测试和保存期间禁用影响快照的输入与重复提交，键盘快捷键同样防重入。
5. 新增主进程 `providers:test-and-save`，并同步更新 contracts、preload 和 IPC 验证。主进程测试捕获的配置，然后在短事务中保存配置、加密密钥与验证记录。网络请求不得包在数据库事务内。
6. 编辑已有配置时携带配置修订标识；测试过程中若配置被其他操作改动，拒绝覆盖并让用户重新加载。
7. 用连接配置修订号和测试范围表达验证状态：记录被测试的模型 ID、能力、连接修订号及时间。密钥轮换只递增修订号，不在 renderer、指纹或日志中保留明文密钥。
8. 列表刷新失败与保存失败分开反馈。保存成功但刷新失败，仍用返回对象更新当前配置，提示列表刷新问题，避免诱导用户重复新建。

### 验收

- 首次创建、编辑已有配置、仅修改别名、换密钥、取消弃改、连续双击、测试失败、保存失败分别测试。
- 测试失败不覆盖原配置，输入仍可修改；保存成功不会新弹“未保存”。
- 新建之后连续点击保存，数据库只保留同一个 provider。
- 测试并保存后卡片状态一致；修改非连接字段不会无故降级成未验证。
- 修复原 articles/reviews 桌面回归的弹窗阻断。

## 4. F02：将改稿意图与候选数量分开

### 用户交互

改稿区域明确区分“在当前文章生成新版本”和“生成备选稿”。前者固定一个结果，后者允许 1—3 个候选。候选生成后可比较、另存或采纳到原文章。

重试按钮写“补生成失败的 1 个备选稿”；旁边显示原文章及基线版本。不得因为这次只补一个，就自动切成写回原稿。

### 契约与数据

建议使用可辨别的输入类型：

```ts
type RevisionPlan =
  | { mode: 'new-version'; count: 1 }
  | { mode: 'new-candidates'; count: 1 | 2 | 3 }

// 两种模式共用：articleId、baseVersionId、draftRevision、
// 基线正文快照、instruction、providerId、model、material references。
```

候选执行项记录 taskId、candidateId、序号、状态、resultArticleId、失败原因和 attemptId。候选 ID 在重试时不变，执行尝试 ID 每次不同，防止结果重复落库。

### 具体开发任务

1. 修改 `ReviseArticleInput`、IPC schema、`ArticlesPage`、`ArticleGenerator` 以及 `ReviewService.apply` 等全部调用方，强制指定 mode。
2. `ArticleGenerator` 根据 mode 决定写入行为，删除 `count === 1` 推导策略。
3. 生成开始前冻结输入。至少保存基线正文、版本、工作草稿修订、用户指令和候选编号；重试不能重新读取已变化的账号定位、框架或正文来假装重试同一任务。
4. 第一小步可先在现有失败请求中保存 mode，立即修复误写；随后在现有任务台账旁增加 revision request/items 存储，使切页和重启后仍可查看及重试。
5. `new-version` 完成时保留现有乐观并发校验。原稿或草稿已变动则保存为独立候选，并明确提示“原稿已更新，本次结果另存为备选稿”。
6. 采纳候选时比较目标原稿版本、草稿修订；有新修改先展示冲突和 diff，不自动覆盖。应用生成新版本，保留候选来源引用。
7. 一个候选只有一个已采纳的成功结果映射；重复回调不能重复新建文章。请求正文只存本地，不记录 API Key，不进入普通诊断日志。

### 验收

- 3 个候选成功 2 个、失败 1 个，补 1 个后原稿版本、正文和草稿完全不变。
- 3 个失败 2 个，补 2 个；连续重试；重启后重试，语义保持不变。
- 生成期间编辑原稿并保存，迟到结果不覆盖用户修改。
- 删除原文章后重试得到明确错误，不写到另一个默认选中文章。
- 将原缺陷复现实验改为上述正确行为断言。

## 5. F03：生成结果完整性、恢复与采纳

### 状态设计

任务执行状态与内容完整性分开：

| 结果情况 | 内容标记 | 默认行为 |
| --- | --- | --- |
| 正常结束且格式有效 | complete | 按用户选定写入模式保存 |
| finishReason 为 length | truncated | 保存可恢复结果，提示输出被截断 |
| 流式接收后断线或取消 | interrupted | 保留已收到内容，不报成功 |
| 明确内容过滤或拒绝 | blocked | 显示原因，不自动按同条件反复重试 |
| 有正文但缺少可识别结束标志 | unverified | 保留并提示需检查完整性 |
| 空响应或格式无法用于文章 | invalid | 展示失败原因；有内容则可查看原结果 |

输出正常结束只表示传输完成，并不证明事实或文章质量合格。

### 具体开发任务

1. 网关保留原始 finishReason，并在公共 helper 归一化为上述结果，不让各生成器各写一套判断。
2. 在版本旁增加生成结果元数据，或增加 `generation_artifacts` 表保存部分内容、来源请求、完成状态和最后接收时间。不要把长正文塞进只用于列表展示的任务摘要。
3. 对新文章的截断结果，任务中心提供“打开未完成内容”；用户可以另存为草稿。对改稿截断结果，原文章当前版本保持不变。
4. 流式内容按时间/大小节流暂存，结束时强制落盘；避免逐 token 同步写 SQLite 阻塞窗口。
5. 显示三个动作：“继续生成”“调整要求后重新生成”“转为手动草稿”。继续生成仍需模型调用，开始前明确基线与输出上限。
6. 续写使用已完成正文尾部及剩余框架；对重复段落给出比较结果，不靠简单字符串拼接直接提交为正式版本。最多自动续接一次，其余由用户主动执行。
7. 已知未完成结果进入排版、复制、推送时给出检查入口。用户可以人工补完并显式“确认内容完整”，解除限制；没有结束标志的兼容供应商不能永久不可用。
8. 既有历史文章标记为 legacy/未记录生成完整性，不追溯阻断全部旧稿；新生成结果按新规则检查。

### 验收

- stop、length、空内容、未知结束原因、断流、主动取消逐一测试。
- 截断改稿不推进原文章版本；重启能找到已收到的部分内容。
- UI、任务中心、文章状态都不将截断结果显示为“成稿完成”。
- 人工补完后能正常保存、排版和导出。

## 6. F05：无需 AI 的图片导入与管理

本项先于 F04 的完整交付验收，方便用用户自己的真实图片测试。

### 用户交互

- 配图页首屏直接提供“导入本地图片”和“让 AI 设计配图”两个入口。
- 手动导入可多选；逐张指定封面或正文用途，封面提供比例预览，正文图提供替代文字和插入位置。
- 文章编辑器增加“插入图片 → 从本地 / 从本文图片选择”；新用户不必先离开编辑器。
- 发布页缺封面时，提供“导入封面”，返回后保留作者、摘要和已选排版。

### 具体开发任务

1. 第一版复用现有 `visual_packs`：新增手动类型，不先将全部资产迁移为另一套归属结构。
2. `VisualPack` 改成明确的 manual/generated 两类。manual 不要求 provider/model/rawXml；generated 保留模型来源。数据库当前这些字段为 NOT NULL，迁移时重建对应表并保留所有 ID、版本绑定和引用，不伪造一个 AI 供应商。
3. 新增 `createManualPack(articleId, expectedVersionId)`，创建文章的本地图片集合。重复导入复用集合，不每导入一张就新建方案。
4. 复用已有字节导入和类型检查，统一文件选择器接受格式、实际校验和错误文案。首版可靠支持 PNG/JPG；其他格式要么显式转换并验证，要么提前说明不支持。
5. 文件名改为随机 ID，资产记录可附内容摘要用于去重；图片先临时写入，登记成功后完成提交，失败清理本次临时文件。
6. 正文使用稳定 asset ID/现有可控协议；替换图片创建新资产引用，避免修改一个共享文件后历史版本图片也改变。
7. 删除前沿用并补全正文、草稿、历史版本、排版和交付快照的引用检查。

### 验收

- 完全没有 provider、账号定位和配图方案，仍可导入文章与三张图片、插入正文、保存、排版、离线导出。
- 单张导入失败不丢其余成功结果；重复文件有明确处理结果。
- 删除仍被历史版本或交付记录引用的图，不造成历史内容破图。

## 7. F04：复制、导出和推送使用明确的图片交付规则

### 将三种交付方式分开

| 方式 | 图片处理 | 完成条件 |
| --- | --- | --- |
| 导出离线 HTML | 读取本地图并内嵌 | 断网、移到另一目录仍显示图片 |
| 复制到公众号 | 处理成目标可读取地址，或明示手动补图 | 不含不可读取的内部协议；实际粘贴验证 |
| 推送公众号草稿 | 上传正文图与封面，保留交付快照 | 预检通过，远端回执或进入待确认 |

### 具体开发任务

1. 从 `WechatPublishService` 提取可复用的图片准备服务：输入排版 ID、文章版本和目标 appId，返回处理后的 HTML、图片数量、失败项与内容摘要。
2. 服务端自行读取排版和资产，不信任 renderer 传来的任意 HTML/路径作为图片上传清单。
3. 缓存继续按 assetId、appId、用途隔离。图片替换采用新 ID；目标账号切换后不复用其他账号的封面标识。
4. 主操作命名为“上传图片并复制到公众号”，明确这会向已配置公众号上传图片；无图片时简化为“复制带格式正文”。
5. 上传前展示目标公众号及图片数，执行中显示进度；同一版内容失败重试只处理未完成图片。
6. 上传成功后重新检查文章版本、排版版本和目标账号是否变化。变化时不把过期结果当作当前交付，提示重新准备。
7. 无公众号连接时提供“复制正文，图片稍后补充”和“导出完整 HTML”。前者将本地图替换为有序占位提示，不把坏协议原样复制后显示图文成功。
8. 复制成功与上传成功分开：上传成功但剪贴板写入失败，可再次复制，无需重复上传。
9. 不把 data URI 作为公众号粘贴兼容性的默认保证。外链图片是否需要导入，继续沿用明确的预检规则。

### 验收

- 无图、单图、多图、缺失文件、目标账号切换、第二张上传失败、剪贴板失败、正文生成新版本分别覆盖。
- 标记“图文已准备”的剪贴板内容不含 `moliu-asset://`。
- 在真实公众号后台粘贴检查图片、表格、列表、标题和代码块；此项属于上线人工验收，模拟测试不能替代。

## 8. F06/F07：统一文章查询、账号语义与目标直达

### 产品决策

- 搜索默认覆盖标题和正文，输入框写“搜索标题或正文”，结果显示命中摘要。
- 顶部“当前账号”影响新建时的默认值和“当前账号”列表过滤，不自动改变已有文章的归属。
- 创作参数单独显示“本次生成使用账号”。用户主动选择的账号或“通用模式”在本次创作中保持不变。
- 路由指定 articleId 时，目标优先级最高。目标被删除则显示明确空态，不自动切到另一篇文章。

### 查询和状态改造

1. `ArticleListQuery` 统一 search、accountId、status、dirtyOnly、offset/limit；筛选与 total 全部由 repository 计算，前端不再二次过滤当前分页。
2. 搜索输入先本地更新，建议 250ms 防抖后提交查询；筛选改变与页码归零作为一次状态更新，避免旧页码查询与新页码查询竞争。
3. 查询 key 包含 resolvedAccountId。异步响应携带请求序号，只接受当前 key 对应的最新结果，旧响应不可覆盖。
4. 文章列表刷新与框架、素材加载分开。输入搜索词不应重新读取整库素材和框架。
5. 首先使用已有 `articles.get(id)` 补齐路由目标，立即解决 500 条限制；随后增加轻量 `getSummary(id)` 并改造选择器分页检索。
6. 选择器每批读取 30—50 条，滚动或搜索继续加载；当前已选项即使不在搜索第一页也单独保留。
7. `ArticleSummary` 逐步去掉全文，只保留 id、title、excerpt、currentVersionId、versionCount、accountId、状态和草稿标记。所有依赖摘要全文的 useWorkDraft 调用必须同步改成加载一篇当前正文，不能直接删字段导致草稿被误判为空。
8. 排版、任务、素材按当前作品或可见范围读取。先测量查询耗时与 IPC 体积，再决定是否加入 SQLite FTS；首版不为解决正确性引入搜索引擎。

### 验收

- 标题命中、仅正文命中、无命中、特殊字符、多页结果的计数与列表一致。
- 当前账号模式下 A → B → A，列表与计数实时正确。
- 快速连续输入三个查询，让旧查询最后返回，界面仍显示最后一次输入结果。
- 准备 501、2000 篇文章，从最旧文章进入评审、配图、排版和发布，文章 ID 始终一致。
- 大列表不再一次 IPC 返回 500 篇全文；记录测试机和数据集后比较性能，不把目标值当作已测成绩。

## 9. F08：推送结果待确认的人工核对流程

### 状态转换

沿用现有 publications 主状态，新增独立的核对记录，避免首版扩大主状态枚举：

- unknown → draft：用户确认后台已收到草稿。
- unknown → failed：用户确认后台未收到，并记录这是人工核对结论。
- unknown → unknown：用户仍无法确认，保持禁止重试。
- draft → published：用户填写正式发布链接，明确标记为人工登记。
- failed → 新交付尝试：保留原记录，记录 retryOf，不能覆写原失败历史。

### 用户流程

点击“核对结果”打开面板，展示目标公众号、文章标题、发送时间、版本和图片数，提供“打开后台”“已找到草稿”“确认未收到”“暂时无法判断”。

“已找到草稿”允许记录远端标识或核对说明；没有可取得标识时标记“用户确认收到，未绑定远端标识”，不伪造 API 回执。“确认未收到”说明误判仍可能造成重复，再由用户明确执行一次重试。

### 具体开发任务

1. 新增 `publishing:resolve-unknown`，输入 publicationId、expectedStatus/修订标识、decision、核对说明以及可选远端 ID。
2. 主进程读取原记录、校验只能处理 unknown；核对记录与状态更新同事务提交。
3. 记录 resolvedAt、resolutionSource=manual、decision。单机未建立身份体系时不伪造“操作人”，使用本地确认来源即可。
4. 重试沿用原不可变快照；若正文已经变化，需要明确选择“重推旧快照”或“使用新版创建新交付”。不能一边声称重试旧稿，一边替换成新正文。
5. 明确失败重试与未知状态保护共用发布互斥检查。页面双击或重复 IPC 不能产生并发交付。
6. 无法承诺跨网络的绝对恰好一次投递；保留未知状态和人工核对，避免把客户端去重当成远端幂等保证。

### 验收

- 服务器已接收但响应丢失、发送前失败、未知结果、旧快照已过期、切换公众号、重复确认和重复点击重试。
- 每次重试能追溯原记录、核对结论与实际使用的版本。
- 未核对的 unknown 记录始终不能直接自动重推。

## 10. F09：正文工作台布局与交互

### 建议布局

普通模式保留侧栏；正文区域结构为“紧凑作品栏 → 编辑工具栏 → 正文/预览”。文章列表可折叠，新建参数放抽屉。完整创作流程只在新建/准备页面默认展示，在正文页可以通过“查看流程”展开。

紧凑作品栏展示文章标题、归属账号、当前版本、保存状态，以及评审/配图/排版/交付入口。不要同时保留两套完整阶段导航。

### 具体开发任务

1. `PageHeader` 增加紧凑模式；`PipelineSteps` 按是否已有当前作品决定默认展开，而非简单在所有页面删除。
2. `ArticlesPage` 分成 ArticleList、ArticleEditor、RevisionPanel、VersionHistory，组件边界按交互职责划分。
3. 增加编辑、双栏、预览三种模式；窄窗口默认编辑，可点击查看预览，不强迫左右挤压。宽窗口由用户选择双栏。
4. “编辑正文”旁保留 Markdown 格式提示，避免仅改文案却让用户误认为是富文本所见即所得编辑器。第一版保留现有文本编辑器与格式工具。
5. “专注模式”收起侧栏、文章列表及新建区，但保存状态和退出按钮始终可见；Esc 可退出，恢复进入前布局。
6. 保存状态统一为“正在本地暂存”“已本地暂存，尚未保存版本”“已保存为第 N 版”“暂存失败，内容仍在编辑区”。对应失败给出重试和复制正文出口。
7. 页面切换返回保留选中文章、光标位置和合理的滚动位置；位置状态按文章保存，不能把 A 的光标应用到 B。
8. 配图和排版入口处理未保存内容时提供“保存版本并继续”“返回编辑”，避免连续出现互相矛盾的暂存/保存提示。
9. 图标按钮有文字或可访问名称；键盘 Tab 可达，焦点清晰；操作提示不只用颜色表达。

### 验收目标

- 在 1366×768 与系统缩放 125%/150% 下检查真实可用 CSS 视口，不把物理像素当布局宽度。
- 768 CSS 像素高度时，紧凑模式正文起点争取在顶部 220 CSS 像素内，可编辑高度争取至少 420 CSS 像素；这是待验收设计目标，不是现状测量值。
- 标题很长、无账号、未保存、生成中、有错误时，头部不挤掉保存按钮。
- 双栏预览保留“模拟效果”说明，主题与正式排版一致时才描述为使用同一渲染规则。

## 11. 创作前半程补齐：账号、热点、选题、框架

### 账号与通用模式

将“通用创作 / 使用某账号定位”做成明确选择，不自动创建空账号。Topics 的输入契约同步支持无账号；模板提供通用受众和风格缺省值。保留现有锁定账号的稳定基线能力，但不要把账号定位作为所有创作入口的硬门槛。

生成任务记录所用账号定位版本。用户修改账号定位后，历史文章不自动改写；下一次生成可选择使用新定位。

### 热点交接

热点到选题携带稳定 ID、标题、来源 URL、来源名称、获取时间和摘要，不只通过临时字符串交接标题。旧的本地存储交接标记可以保留兼容读取，但新流程用类型化的路由 ID 或持久化创作上下文。

生成前展示已选热点，允许移除。来源不可访问时保留快照并标记来源待核实，不阻止用户手动构思，也不把缓存内容描述成已实时核验。

### 框架确认

从选题/素材进入框架时保留已选输入，生成后展示核心观点、读者收益、段落安排、每段参考素材和待补事实。按字段编辑后再生成正文。

已有手动框架仍可直接使用，不强迫每篇文章都填完整确认卡。没有证据支持的段落显示“需要补充依据”，用户可以删掉该段或补素材。

### 任务反馈

多候选任务显示“已完成 1/3，1 项失败，1 项进行中”，按任务/候选 ID 关联流式事件。未知总时长不显示假百分比。切页后任务继续在任务中心可见；取消后明确保留哪些已完成结果。

验收：从不同入口最终生成请求的主题、账号、素材均与确认页一致；返回补资料不丢已填内容；不使用账号也能完成通用选题。

## 12. F12：长素材保留、分段与上下文预算

### 数据模型

建议在现有 Material 之外增加素材版本/正文片段记录：materialId、versionId、完整提取文本、原文件名、内容摘要、解析时间，以及 chunkId、heading、charStart/charEnd、文本内容。解析器能稳定提供页码时记录页码，否则只显示章节/字符区间，不编造页码。

文件原件可作为可选资产保留。原件保留与否、解析上限及磁盘占用在导入结果中说明。已有被截断素材无法凭空恢复，标记 legacy-partial，允许重新导入补齐。

### 具体开发任务

1. 去掉“截断后仍作为完整资料保存”的行为。对支持范围内文件保留完整提取文本；超出安全解析上限时明确失败或征求分段导入，不静默截断。
2. 解析在受控工作线程/任务中执行，设置字节、解压和文本规模上限，防止大型文档阻塞 Electron 主进程。
3. 按标题、段落和句子边界分块，首版采用关键词与章节匹配；可先使用本地 SQL 查询，确认召回效果后再决定是否引入向量能力。
4. 模型上下文预算 = 模型上限 − 系统提示 − 用户任务 − 必要正文/框架 − 输出预留 − 安全余量。优先使用适配模型的 token 计数；未知模型采用保守估计并标注“估算”，不能把字符数当作精确 token 数。
5. 超预算时先筛选最相关片段，展示“选中 5 份资料，本次使用 12 个片段”；提供查看片段、补选和移除，不用“AI 已阅读全部资料”的文案。
6. 将实际使用的片段 ID 与版本写入生成输入快照。文章事实核查可以回到该版本原文，而不是素材最新修改后的内容。
7. 引用摘要是派生内容，保留回到原文的链接。模型生成摘要不能自动变成事实证据。

### 验收

- 用关键结论在开头、中间、末尾的资料集测试召回和提示行为。
- 用多文档超过预算场景验证选择范围与实际请求一致。
- 重新导入同一资料后，旧文章仍能查看当时引用版本。
- 不支持扫描 PDF 时明确提示需要 OCR/文字版，不把空解析当成功。

## 13. F10：有证据的事实评审与受控采纳

### 首版能力边界

先实现“正文断言与已导入资料核对 + 用户补充证据”，不把自动联网检索设为必需。只有语言模型指出疑点时显示“待核实”，不能显示“已确认错误”。

### 具体开发任务

1. ReviewProblem 增加 kind（语言/结构/事实/引用）、原文片段及版本、证据引用数组、核实状态和采纳状态。
2. 事实与引用类默认未采纳；批量采纳语言修改时不夹带事实类修改。第一版也可统一默认未采纳，提供按类别全选。
3. 评审输入携带原文和真正用于生成的素材片段，要求返回来源 ID 与摘录。主进程核对 ID 存在、引用属于该输入、摘录能在源片段定位；校验失败回退为未核实。
4. 证据状态用“待核实 / 有资料支持 / 资料冲突 / 资料不足”，另存人工确认结果。来源支持某个说法不等于该说法绝对真实。
5. 右侧面板展示正文句子、建议、来源和摘录。用户可打开资料、补链接、填写核对说明。
6. “应用选中建议”先生成备选稿，展示 diff，再采纳为新版本。沿用 F02 的版本并发校验；生成过程中原稿变化不能覆盖。
7. AI 实际改动超出选中意见时全部显示，不以“只采纳两条建议”暗示模型一定只改两处。数字、日期、实体、引用改动做额外高亮，仍允许人工审阅全文。
8. 手工修改正文后，依赖旧片段的评审标记过期。不能将旧版“有资料支持”状态直接套到新版断言。

### 验收

- 有来源、无来源、伪造来源 ID、数字冲突、摘录不匹配分别测试。
- 未采纳的事实类意见不会进入改稿指令。
- 应用后生成独立结果，用户未确认前原稿不变。
- 不访问真实外部事实源的测试只证明流程，事实可靠性另用人工样本集评估。

## 14. F11：备份导出、导入与恢复

### 用户交互

保留“创建本地恢复副本”，另提供“导出备份包”“从备份包恢复”。列表显示创建时间、文章数、图片数、大小和校验结果。外部导出成功与本地副本成功分别记录。

### 具体开发任务

1. 保留现有内部目录限制。外部读写只通过主进程系统文件对话框取得的授权路径执行，不能直接把 `insideData` 删除后接受任意 renderer 路径。
2. 首版可导出一个自包含目录；若打包单文件，选用现有可用依赖或经审查的归档库，并校验路径穿越、符号链接、文件数、单文件大小和解压总量。
3. manifest 包含格式版本、schema 版本、应用版本、文件清单、大小、hash、文章/资产计数及是否包含凭据。
4. 默认可携带备份不包含密钥、登录 cookie；账号定位、文章和非敏感服务配置保留。若允许同机凭据副本，明确它与 Windows 用户绑定，跨机器恢复需要重新录入。
5. 生成、暂存、上传等写操作进行中时沿用 operation gate，或统一冻结写入后取一致快照；图片和数据库必须来自同一个逻辑时点。
6. 导出到临时目录，完整校验后再以最终名称呈现。磁盘不足或取消时不显示成功，并清理本次临时输出。
7. 导入先在 staging 验证清单、hash、数据库结构和受支持版本；展示恢复预览，再执行替换。恢复前创建回退副本，失败自动还原。
8. 高于当前程序支持版本的备份拒绝恢复；低版本先对 staging 副本迁移。恢复成功清空 renderer 草稿缓存和选择缓存，重新加载数据库。
9. 备份范围覆盖新增任务结果、手动图片、素材正文/原件、证据与发布核对记录，不能只复制旧版图片表涉及的文件。
10. 首版使用应用内提醒和用户设置的保留策略。自动清理只针对已确认由应用创建且不在使用中的本地副本，不删除用户导出的包。

### 验收

- 当前环境恢复、全新数据目录恢复、去密钥导出、旧版本迁移、未来版本拒绝、损坏 hash、缺文件、磁盘不足、恢复中断、路径穿越分别测试。
- 恢复后核对文章数、版本数、草稿、图片、任务结果和发布记录。
- “复制到另一目录后可恢复”与“另一台电脑能解密凭据”是不同测试，不能互相替代。

## 15. 发布复盘的可用改进

首版继续手动记录，新增可选指标：统计截止时间、阅读数、分享数、净增关注、用户自行填写的转化数。空值代表未记录，不能自动算作零。

复盘绑定发布记录、文章版本和账号，显示目标与实际值；“已发布”注明手动登记来源。可将经验提议保存到账号记忆，但自动学习前展示具体内容，避免单篇结果被直接固化为永久写作规则。

验收重点是字段解释、日期口径、空值处理和数据归属。自动抓取公众号后台数据作为后续独立需求，先确认官方可用能力与实际权限。

## 16. 数据升级与代码组织

### 数据升级

- 使用现有 schema_migrations 建立有序迁移；新增字段默认值明确，迁移可重复检测但不能重复应用。
- 涉及 visual_packs 的 NOT NULL 改动、CHECK 约束或引用关系调整时，在事务内重建表并校验外键和行数，不能只修改 TypeScript 类型。
- 升级前生成恢复副本。迁移失败保留原库，显示可理解的错误；老程序不能直接读取新 schema 时明确拒绝并引导用匹配版本或恢复旧副本。
- 旧文章缺少生成结束原因时不批量判为失败；旧素材缺失的尾部内容不伪造；旧模型生成方案明确回填 generated。
- 每次 schema 更新将备份/恢复同步纳入验收。

### 渐进式文件拆分

| 边界 | 建议职责 | 避免的问题 |
| --- | --- | --- |
| provider service/form | 测试保存与表单加载分开 | 保存操作误走用户切换确认 |
| article query/selection | 列表查询、当前目标加载、分页 | 每页重新实现筛选与 500 条假设 |
| revision service | 不可变输入、候选、采纳 | 数量与写入对象耦合 |
| generation result helper | 完整性归一化、部分内容保留 | HTTP 成功被误认为成稿成功 |
| delivery asset service | 图片准备和目标账号缓存 | 复制、导出、推送处理分散 |
| publication resolution service | 核对与受控重试 | 状态存在但没有合法操作出口 |
| material context builder | 片段选择与预算 | 各生成器任意截断资料 |

按修复任务提取相关模块即可。不为了减行数制造大量仅转发参数的包装层，也不在一次提交里同时迁移数据库、换编辑器和重做页面。

## 18. 测试与完成标准

### 当前基线

审查时原有 250 项单元测试通过、构建与类型检查通过；桌面 12 组通过 9 组。不要把缺陷复现测试通过计入“功能正常”的证明。

### 必须修复的回归断点

- 修 F01 后重新运行 articles/reviews，按新测试保存语义更新旧状态断言，不用强制点击穿过遮罩。
- layouts 使用精确文章控件定位，避免“文章”与“文章类型”歧义；再验证完整流程。
- 将 audit-review 三个实验转成期望正确行为的测试，加入异常与并发输入。

### 最终场景验收

1. 零配置：导入已有稿 → 插入本地图 → 保存 → 排版 → 移到新目录离线打开导出文件。
2. 新用户 AI：首次配置 → 通用主题 → 框架 → 正文 → 修改 → 重启后恢复。
3. 部分失败：三个候选一个失败 → 改动原稿 → 补生成 → 原稿不被覆盖。
4. 截断：模型输出 length → 部分内容保留 → 人工补全或续写 → 正确采纳。
5. 多账号大库：2000 篇、多个账号 → 搜正文关键词 → 直达最旧文章各阶段。
6. 真实交付：本地图文复制到公众号、推送草稿箱、实际微信预览逐项检查。
7. 不确定交付：模拟远端收到但回执丢失 → 核对 → 正确归档，不自动重推。
8. 恢复：导出备份 → 新数据目录恢复 → 文章、版本、图片、素材、任务及记录一致。

### 建议观察的产品指标

先建立本地测试或经用户同意的试用记录，不默认上传正文和操作遥测：首次成功导出的完成率与步骤数、误触发弃改弹窗次数、丢失草稿次数、错误写回原稿次数、无法恢复任务数、交付待确认未处理数、搜索计数不一致次数。

其中误写原稿、丢失已确认保存内容、未完成结果误报成功，应作为必须为零的发布检查项。耗时、阅读空间和首次完成率先测基线，再设目标，不能用未经测量的提升百分比包装优化效果。
