# 排版与发布能力调研报告

> 调研日期：2026-10-05
> 目的：为「排版 + 发布」这两块短板找到可借鉴的开源方案，并判断哪些能直接用、哪些只能借鉴思路
> 方法：核验GitHub 仓库真实授权链与代码，检索公众号实战文章，结论全部落到本项目代码上验证

---

## 一句话结论

**先修一个 S0 级发布缺陷（正文图片必然被微信过滤），再修两个会导致"格式散架"的结构问题（`<pre>` 不在白名单、class 未剥离），最后才是补版式组件。开源代码一个都不能直接搬——授权链全部不可用。**

> **补充（2026-10-05晚）**：P0 已修复，详见 `docs/排版与发布优化方案.md`。
> 实测juice 输出后又发现两个结构性问题（`<pre>` 不在微信白名单、`class` 未剥离），
> 已提升为 P1，优先级排在版式组件之前。

## 一、先说最重要的：我们有一个 S0 级发布缺陷

调研过程中发现的，不是"欠缺"，是**明确的功能性 bug**。

### 微信官方要求（已核验官方答复）

微信服务市场官方技术运营专员对 `draft/add` 的明确答复：

> "涉及图片 url 必须来源「上传图文消息内的图片获取URL」接口获取。**外部图片 url 将被过滤。**"

多个实战来源一致指出：草稿箱接口会**主动过滤**非微信图床（`mmbiz.qpic.cn`）的图片，且微信对非微信域名图片有 Referer 防盗链。

### 我们的实现现状（已逐处核验）

```
项目实际调用的微信接口：
  cgi-bin/token                    ✓ token
  cgi-bin/material/add_material    ✓ 封面素材
  cgi-bin/draft/add                 ✓ 新增草稿
  cgi-bin/media/uploadimg          ✗ 未调用← 缺失
```

排版稿里的图片地址是 **`moliu-asset://` 自定义协议**（`contracts.ts:653`，本机文件协议，微信服务器无法访问）。

`VisualAsset` 有 `wechatMediaId` 字段（`contracts.ts:660`），但主进程里它**只用于封面**：

```ts
// wechat-publish-service.ts:111
private async resolveThumbMediaId(input) {
  if (input.coverAssetId) {
    const asset = await this.uploadAsset(input.coverAssetId)  // ← 只有封面走这里
    return asset.wechatMediaId!
  }
}
```

而 `draft/add` 直接把 `layout.html` 塞进 `content`（第 67 行），**正文里的 `<img src="moliu-asset://...">` 原样送出**。

### 后果

**任何带图文章推到草稿箱，正文图片 100% 丢失**。用户会看到"文字都正常，就是没有图"。

这个缺陷很隐蔽：因为排版预览里图片是正常显示的（`moliu-asset://` 在本机可访问），只有推到微信后才消失——用户很难归因。

### 修复方案（已明确，约 40 行）

推送前新增一步：

```
1. 遍历 layout.html 里的 <img src="moliu-asset://xxx">
2. 对每个未上传过的图，调用 cgi-bin/media/uploadimg
   （注意：不是 material/add_material，两者返回类型不同，不能混用）
3.拿回 mmbiz.qpic.cn URL，替换 src
4. 顺带补上 width:100% 处理（微信会强制覆盖图片宽度）
5. 再调 draft/add
```

⚠️ **两个接口的坑**（多个来源共同指出）：

| 用途 | 接口 | 返回 |
| --- | --- | --- |
| 正文插图 | `cgi-bin/media/uploadimg` | 图床 URL，可放content |
| 封面素材 | `cgi-bin/material/add_material?type=image` | `media_id`，填 `thumb_media_id` |

用错接口拿到的 URL 放进正文，图片同样会被过滤。**这两个千万别混。**

顺带要补的字段限制（`draft/add` 会拒绝）：

- `title` ≤ 32 字（超了报 45003）
- `digest` ≤ 128 字
- `content` < 2 万字符且 < 1MB

## 二、开源项目核验结果（含授权链）

我对每个项目都做了GitHub 仓库与LICENSE 的实际核验，而不是看推荐文章。

| 项目 | Stars | License | 能直接用吗 | 核验结论 |
| --- | --- | --- | --- | --- |
| **gzh-design-skill** | 2.9k | **AGPL-3.0** | ❌ | 设计思想极有价值，但**衍生品必须开源**。我们是闭源桌面应用，**绝对不能复制代码** |
| **Wechatsync** | 1.4k | GPL-3.0 | ⚠️ 部分 | 核心适配器已私有化为 git submodule，**核心逻辑并未开源**；但架构模式值得学 |
| **md2wechat (sszgr)** | — | 有 LICENSE | ⚠️ 部分 | 纯前端、MIT 友好型；**只到"复制到公众号"，不做 API 发布**，与我们的发布链路不重叠 |
| ~~md2wechat (lyricat)~~ | — | — | ❌ | **仓库 404**。搜索结果里的这个地址是错的，印证了 ADR 0007 的判断 |
| **multi-publisher** | — | MIT（自称） | ⚠️ | 9 平台适配器中"仅 2 个已实测"，成熟度存疑 |
| **PostBot** | 1.4k | Apache-2.0 | ❌ 不建议 | 商业产品的开源版，核心为闭源 SaaS |

### 关于 ADR 0007 的补充

ADR 里说 md2wechat "repository 字段缺失"——这次核验发现更准确的情况是：**网上流传的`lyricat/md2wechat` 地址根本不存在（404）**，而 `sszgr/md2wechat` 是另一个纯前端项目。

**结论不变且更强了：md2wechat 无法作为依赖引入。** 建议更新 ADR 记录这个细节。

## 三、值得借鉴的：gzh-design-skill（借鉴设计，不碰代码）

这个项目虽然 AGPL 不能抄代码，但**它的设计思想几乎是为我们量身定做的**。

### 最值得学的一条：确定性下沉脚本

它的核心设计原则：

> "平台限制这类死规则交给校验脚本，模型只做内容判断。"

它有两道关卡：
- `component_lint.py` —— 组件库源头检查
- `validate_gzh_html.py` —— 最终产物合规校验

**这正好命中我们的问题。** 我们现在把公众号平台限制（37 标签白名单、禁 class/div、必须内联）**散落在 juice 配置和正则里**，没有一处能"确定性验证产物是否合规"。

**借鉴方案（思路，不抄代码）：**

在 `article-layout-service.ts` 旁加一个 `validate-layout.ts`，把平台限制写成可执行的断言：

| 检查项 | 依据 |
| --- | --- |
| 无 `<div>` / `<script>` | 微信白名单约 37 标签 |
| 无 `class` / `id` 属性 | 微信强制移除非内联属性 |
| 无 `position:fixed/absolute/sticky`、`float`、`display:grid` | 官方过滤规则 |
| 所有文字被 `<span leaf="">` 包裹 | 微信正文渲染必需 |
| 标题 ≤32 字、摘要 ≤128 字 | `draft/add` 字段限制 |
| 无外链图片（`http`/`https` 开头且非 `mmbiz.qpic.cn`） | 会被过滤 |

**在「生成排版稿」和「推送到草稿箱」两个时机都跑一遍，不合规就明确报出来。**

这类校验的价值在于：**用户不需要懂公众号技术规则，AI 也不需要"记得"这些规则**。

### 第二条值得学的：主题的"配方表"思想

它的 6 套主题不只是一堆 CSS，而是每套都带：
- **设计变量**（主色、灰阶）
- **视觉层级表**（标题几级、各级字号间距）
- **文章类型配方表**（说理性/ 叙事型 / 教程类分别推荐哪些组件）

我们现在的 `layout-themes.ts` 只有 5 套纯 CSS（`wechat-green` / `magazine` / `tech-blue` / `warm-paper` / `minimal`），**没有元信息、没有文章类型适配**。

**借鉴方案**：给每个主题补一份元信息，用户选主题时能看到"适合什么类型的文章"，而不是面对 5 个色块盲选。

### 第三条：主色克制原则

> "主色只在锚点出现（全文 ≤5 处），大面积白底 + 灰阶，彩色只做点缀。"
> "约 90% 的文字交给一套中性灰阶，色彩不承担正文阅读。"

这条正好呼应我们刚做的可读性整改——**彩色的功能是标重点，不是承载正文**。可以写进主题设计规范。

## 四、值得借鉴的：Wechatsync（架构模式）

### 它最聪明的一点：复用浏览器登录态

```
你的浏览器（已登录各平台）
    ↓ 扩展读取 Cookie
    ↓ 调用平台官方 Web API
各平台（知乎 / 掘金 / 头条 / ...）
```

**不模拟登录、不碰验证码、不经过第三方服务器。**

这与我们项目"密钥不进渲染进程、不走 .env"的边界理念高度一致。**但我们目前只支持微信公众号**（`LayoutPlatform = 'wechat' | 'xiaohongshu' | 'web'`），且小红书/知乎等平台没有 API 权限。

**结论：现阶段不适用。** 如果未来要做多平台，**它的适配器协议设计**（统一 `sync_article` 接口 + 平台 ID + 登录态检查）值得参考——但要注意它的核心适配器已私有化，拿不到实现。

### 一个可以直接借用的能力

它有个功能叫 **「网页转 Markdown」**：

> 任意网页智能提取正文，自动过滤广告噪音，图片本地化，打包为 Markdown + 图片 ZIP

我们已经有「导入现成稿」和「素材库」。**"从竞品公众号文章提取正文作为参考素材"** 这个场景我们没有——这可能是选题灵感的重要来源。

但要谨慎：直接复制他人文章有版权风险。建议定位为**"提取结构与排版作为参考，不复制内容"**，且只提取自己已授权的账号。

## 五、We need 公众号 / 知乎等平台的"排版样式库"

调研中发现**秀米、135编辑器** 这类产品的成功，恰恰说明一件事：

**排版的价值不在"把 Markdown 转成 HTML"，而在"提供成体系的设计选择"。**

它们的核心资产是几百套**经过设计验证的版式模板**（标题样式、引用块、分割线、卡片、序号、时间轴……），而不是转换器。

对我们（不做在线编辑器）的启示：

| 我们该做 | 我们不该做 |
| --- | --- |
| 主题 + 组件配方（引言卡、金句、序号章节、目录） | WYSIWYG 可视化编辑器（成本极高，且不是我们的差异化） |
| 提升"成稿的可读性上限" | 无限自由样式 |

**具体可加的组件（都是公众号高频需求，我们目前一个都不支持）：**

| 组件 | 用途 | 我们有吗 |
| --- | --- | --- |
| 引言卡/ 摘要块 | 开头三行决定用户是否继续读 | ❌ |
| 章节自动编号 | 长文结构清晰 | ❌ |
| 金句 / 划线标记 | 视觉锚点 | 部分（`mark`） |
| 目录 | 长文导航 | ❌ |
| 分割线变体 | 段落呼吸感 | ❌ |
| 提示 / 警告块 | 引用、数据结论 | ❌ |
| 表格美化 | 微信里原生表格很丑 | ❌（`table` 未做样式） |
| 脚注 | 学术类内容 | ❌ |
| 公式（KaTeX） | 技术/教育类 | ❌ |

**特别提醒**：如果你的目标用户是"体制内考试"相关内容（你的既有定位），**表格和公式不是锦上添花，是刚需**。

## 六、我们 vs 开源方案的能力差距

| 能力 | 我们 | md2wechat | gzh-design | 目标 |
| --- | --- | --- | --- | --- |
| 排版引擎 | markdown-it + juice | markdown-it + juice | 组件库 | ✅ 够用 |
| 主题数 | 5 套纯 CSS | 多套 + 可自建 | 6 套体系（含元信息） | ⚠️ 缺元信息与组件 |
| **正文图上传微信** | **❌ 未实现** | 不做（走复制） | 不做（走复制） | **🔴 P0** |
| 封面图上传 | ✅ | — | — | ✅ |
| 微信 API 推送 | ✅ | ❌ | ❌ | ✅ 我们的优势 |
| 版式组件 | ❌ | 片段 | 数十种组件 | ⚠️ **最大短板** |
| 平台合规校验 | ❌ | ❌ | ✅ 双关卡脚本 | 🔴 P1 |
| 跨平台分发 | ❌ | ❌ | ❌ | 不做（超范围） |
| AI 排版 | ✅ 生成 HTML | ❌ | ✅ 组件装配 | ✅ |

**结论：我们的引擎和发布链路是强项，短板在"版式组件"和"合规校验"两处。**

## 七、建议的行动清单

### P0 — 修复发布缺陷（必修，约 0.5 天）

> 正文图片调`media/uploadimg`，替换 `moliu-asset://` 为微信图床 URL。

这是**功能性 bug，不是优化**。用户发带图文章必然丢图，且会归因成"软件不好用"。

同时补字段长度校验（title ≤32、digest ≤128），否则会收到微信的错误码而不知所以然。

### P1 — 加排版合规校验（1 天）

> 新增 `validate-layout.ts`，把微信平台限制写成可执行断言，在生成排版稿与推送前各跑一次。

**这是投入产出比最高的一项**：一次开发，让 AI 和用户都不再需要懂公众号技术规则。

同时补 `<span leaf="">` 包裹与图片 `width` 处理。

### P2 — 版式组件库（3-5 天）

> 优先做高频组件：引言卡、章节自动编号、目录、分割线变体、提示块、表格样式。

同时给 5 套主题补元信息（适合的文章类型 + 视觉层级），并明确"主色 ≤5 处、90% 文字走灰阶"的规范。

### P3 — 暂不做

| 想法 | 原因 |
| --- | --- |
| 引入 md2wechat | 授权链不可用（404 /无 LICENSE） |
| 复制 gzh-design 代码 | AGPL-3.0 会传染，闭源产品不可用 |
| 多平台分发 | 超出当前产品范围，且核心适配器未开源 |
| 可视化编辑器 | 成本极高，不是差异化方向 |
| 从竞品文章提取素材 | 有版权风险，除非限定为已授权账号 |

## 八、核验方法说明（可复现）

本报告所有结论都经过实际核验，而非依赖推荐文章：

| 结论 | 核验方式 |
| --- | --- |
| md2wechat (lyricat) 不存在 | WebFetch 该仓库 URL → 返回 404 页面 |
| gzh-design-skill 是 AGPL-3.0 | 读取其README 的 License 章节原文 |
| Wechatsync 适配器已私有化 | README 提交记录含 `privatize adapters via git submodule` |
| 我们没调 uploadimg | `grep -rn "media/uploadimg" src/main/` → 无结果 |
| 图片是本地协议 | `contracts.ts:653` 注释 + 字段定义 |
| wechatMediaId 只用于封面 | `wechat-publish-service.ts:111` 唯一调用点 |
| 微信会过滤外链图 | 微信服务市场官方技术运营专员答复 + 4 个独立来源交叉验证 |

> **一个提醒**：调研中搜到的推荐文章普遍**不核验授权链**（如某篇文章把`lyricat/md2wechat` 列为 3.5k stars 首选，但该仓库根本不存在）。**引入任何依赖前必须实际访问仓库、读 LICENSE 文件**，这是 ADR 0007 立下的规矩，本轮再次验证了它的价值。
