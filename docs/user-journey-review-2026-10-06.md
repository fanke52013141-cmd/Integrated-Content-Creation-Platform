# 公众号文章创作项目：用户旅程与代码审查

审查日期：2026-10-06。对象：当前工作区的心流 Desktop 0.2.0。

结论：功能链路已相当完整，草稿持久化、历史版本、发布预检、备份回退等基础值得保留。但仍存在首次配置误报、批量重试改变写入对象、截断正文被判成功，以及图文复制缺少图片交付处理等问题。建议优先修复这些可靠性问题，再调整界面与内容质量辅助能力。

本次没有修改产品实现。增加了本报告和 `tests/audit-review.test.ts` 三个缺陷复现实验。实验通过表示成功复现当前缺陷，不表示缺陷已经修复。

## 审查方法与验证边界

- 沿首页 → 服务配置 → 账号 → 热点 → 选题 → 素材 → 框架 → 正文 → 评审 → 配图 → 排版 → 交付 → 复盘与备份检查页面、IPC、服务和持久化逻辑。
- 运行项目已有 Electron 自动化流程，检查实际窗口截图。使用脚本的隔离测试数据目录，不使用真实创作数据库做写入实验。
- 原有单元测试：26 个文件、250 项通过。
- 类型检查和生产构建：通过。
- 12 组桌面冒烟测试：9 组通过，3 组失败。通过 electron、hotspots、topics、materials、frameworks、visuals、publishing、workspace、workflow；失败 articles、reviews、layouts。
- articles、reviews 被 AI 配置保存后的意外确认弹窗阻断，见 F01；layouts 因 `getByLabel('文章')` 同时匹配“文章”和“文章类型”而失败，属于脚本选择器问题。该失败不能用来认定排版功能有缺陷，也不能宣称该组流程已验证完毕。
- 新增三个定向实验复现 F02、F03、F06 的搜索部分。运行方式：`node node_modules/vitest/vitest.mjs run tests/audit-review.test.ts`。
- 模型生成与公众号发布主要通过模拟接口验证；没有使用真实付费模型验证文章质量，没有向真实公众号推送，没有在微信客户端检查最终显示。没有进行完整依赖漏洞扫描或逐行安全审计。

## 按实际创作步骤审查

| 步骤 | 当前表现与问题 | 为什么值得优化 | 具体方向 |
| --- | --- | --- | --- |
| 1. 首次进入 | 首页提供主题、热点、资料和导入文章四种入口，这是合理的；进入正文后导航和头部区域过多 | 用户首次产出所需步骤和写作空间比功能入口数量更重要 | 保留首页多入口；正文页采用紧凑作品栏和专注模式，见 F09 |
| 2. 配置 AI | 首次保存成功后又提示“有未保存的修改”；保存前测试结果与列表验证状态分离 | 最早的信任环节就出现矛盾反馈 | 原子化保存、更新表单基线并记录对应配置的验证结果，见 F01 |
| 3. 账号定位 | 已有问答草稿、版本和锁定；但顶部当前账号、列表过滤账号、生成目标账号是不同状态 | 多账号用户容易误以为切换顶部账号就切换了所有创作上下文 | 明确显示“本次生成使用账号”；当前账号过滤必须随切换重新查询，见 F06 |
| 4. 热点洞察 | 已有多源聚合、收藏和筛选；热点适合作为方向输入 | 热度和事实可靠性是不同维度，直接拿标题写文章容易丢上下文 | 在进入选题时保留来源、更新时间和原文入口；将核实事实列为后续动作，不将热度作为真实性证明 |
| 5. 选题生成 | 页面要求已有锁定账号，正文和框架却支持不使用账号 | 首页“账号可选”的心智与选题模块的硬前置条件不同 | 支持通用选题模式，或在入口明确说明“个性化选题需先锁定账号”，提供直接写框架的出口 |
| 6. 搜集素材 | 支持搜索、手动录入、文件导入和引用追踪；长文导入及框架输入有截断 | 用户选择了资料，不等于模型看到了资料中的全部结论 | 展示实际使用范围，长文分段、检索与出处定位，见 F12 |
| 7. 生成框架 | 模板、账号、主题、素材都有入口；可以绕过选题 | 用户应在花费正文生成成本前检查结构是否真的对应资料 | 增加框架确认卡：读者、核心观点、段落依据、缺失事实；减少对 XML 展示的依赖 |
| 8. 写作与改稿 | 本地暂存、历史版本和改稿基线检查较完整；重试语义和生成完整性有缺陷 | 原稿不应在“补候选”时被意外切换版本，半篇文章不应被报成功 | 见 F02、F03；先修复写入语义与完成状态，再优化编辑体验 |
| 9. 内容评审 | 支持多角色和过期意见检查；事实核查角色只收到正文，问题默认采纳 | 用户可能把语言模型的建议当成事实已被核实 | 将风险提示与证据核实分开；事实修改要求显式采纳与证据，见 F10 |
| 10. 配图 | 支持生图、导入与插入正文；首次导入本地图依赖先生成 AI 方案 | 已有稿件和封面的用户仍被迫配置文本模型 | 支持无 AI 创建手动配图集合，见 F05 |
| 11. 排版与导出 | 有主题、预览、格式检查和单文件 HTML 导出；带格式复制直接输出内部图片协议 | 应用内看得到不代表公众号编辑器能读取 | 交付前处理图片地址，见 F04；明确预览是模拟效果 |
| 12. 推送草稿箱 | 版本过期、未保存正文、缺图等均有预检；不确定状态缺少完整人工核对出口 | 用户核对完后台后仍无法让记录回到准确状态 | 增加“已找到草稿 / 确认未收到”的状态转换，见 F08 |
| 13. 发布与复盘 | 公众号正式发布在后台完成，应用手动记录链接和复盘 | 现阶段不能把手动记录等同平台数据自动同步 | 清楚标注手动状态；优先加入阅读、分享、关注转化等可选指标及目标对比 |
| 14. 备份与长期使用 | 备份有数据库和图片校验、失败回退；默认副本仍在同一数据目录 | 只能覆盖部分误操作恢复需求，不能替代异地副本；文章增长后还有 500 条边界 | 支持导出/导入备份包和备份提醒，解决旧文章下游不可选问题，见 F07、F11 |

## 需要优先修复的具体问题

优先级：P1 为可能改变用户内容或破坏核心交付的高优先级缺陷；P2 为特定场景下的功能缺口或明显体验问题；“建议”为产品优化，不表示已复现运行错误。

### F01 · P1 · 首次保存 AI 服务后出现错误的未保存确认

- 触发：新建空白配置，填写密钥和模型，点击“测试并加密保存”。
- 证据：`src/renderer/src/pages/ProvidersPage.tsx:270` 保存后调用 `chooseProvider(saved)`；`:139` 在新 ID 与旧 `selectedId` 不同时进入 `guardUnsavedForm`，而此时表单基线仍是保存之前的值。
- 结果：数据库已经保存，界面却提示继续操作会丢弃未保存修改。两个 Electron 套件被该遮罩阻断。若取消确认，表单仍可能保留新建态，后续保存存在重复建配置的风险。
- 优化：抽出无交互的 `loadProviderIntoForm`；保存成功直接载入返回对象、清空密钥输入、更新基线和选中 ID。只有用户主动切换不同配置时调用未保存检查。
- 关联问题：`testDraft` 的成功不会自然成为保存后 provider 的验证记录，因此“测试通过并保存”后列表仍可能显示未验证。将验证记录绑定配置指纹，或由主进程提供一致的测试并保存操作。
- 验收：新建成功后无弃改弹窗、输入框中的明文密钥清空、再次保存不创建重复项；当前配置的验证状态与刚完成的测试一致。

### F02 · P1 · 补一个失败改稿候选会修改原文章

- 触发：选择三个改稿候选，两个成功、一个失败；点击“只补生成 1 篇”。
- 证据：`ArticlesPage.tsx:190` 将原请求的 `count` 改为失败数量；`src/main/services/article-generator.ts:134` 用 `count === 1` 判断是否写回原文章。
- 结果：首次多候选生成会新建文章，但补生成一个时会推进原文章的当前版本。历史版本仍在，不是不可恢复的数据删除；问题在于补候选意图被改成写回原稿。
- 验证：定向实验用真实内存数据库和模拟模型复现了“两成功一失败 → 重试一篇 → 原文章版本变为 2”。
- 优化：将候选数量与写入方式分开，显式保存 `revisionMode: 'new-candidates' | 'new-version'`；重试沿用原模式和基线。候选采纳由用户单独执行。
- 验收：不论失败数量是多少，补候选都不改变原稿 ID、当前版本和工作草稿。

### F03 · P1 · 因输出长度限制截断的正文仍被保存为成功成稿

- 证据：`article-generator.ts:91` 和 `:138` 只将 `response.content` 交给 Markdown 校验；网关已经提供 `finishReason`，但生成器没有检查它。正文和改稿调用设置了 8000 的最大输出 token 数。
- 触发：模型返回 `finishReason: 'length'`，正文已有一级标题但结尾尚未写完。
- 结果：仍返回成功文章，用户看到生成完成，后续可以排版和交付半篇内容。
- 验证：定向实验返回 `length`，结果依然是一个成功文章、零失败。
- 优化：保存为“生成未完成”的可恢复草稿并提示续写；必要时提供提高长度或缩短要求的操作。不要静默丢弃已生成文字，也不要无限自动重试。
- 验收：`length`、内容过滤等非正常结束原因进入明确状态；截断稿不能被误报为完整成稿。

### F04 · P1 · “复制图文”保留应用内部图片地址

- 证据：`LayoutsPage.tsx:141`、`:291` 将 `selected.html` 原样传给 `clipboard.writeRichText`；`src/main/ipc.ts:699` 原样写剪贴板，没有执行公众号推送服务中的图片上传和 URL 替换。
- 触发：正文包含 `moliu-asset://` 图片，使用“复制图文（带格式）”。
- 影响：内部图片协议只有本应用能解析，公众号编辑器无法靠这些地址取得图片；“可直接粘贴”的成功提示没有覆盖图片交付条件。本次没有到真实微信后台复现最终粘贴表现。
- 优化：对公众号复制执行图片就绪检查；已配置公众号时上传图片并替换为微信可访问地址。未配置时明确说明正文样式可复制、哪些图片还需手动上传。单文件 HTML 内嵌图适用于离线导出，但不能据此保证微信粘贴接受 data URI。
- 验收：公众号复制结果不含内部协议；真实后台粘贴后逐张核对图片，不仅核对文字样式。

### F05 · P2 · 不使用 AI 时，首次本地图导入入口走不通

- 证据：`VisualsPage.tsx:333` 只有已存在方案时才渲染带“导入本地”的卡片；`:305` 创建方案依赖模型。`visual-asset-service.ts` 的 `importFromBytes` 也要求已有 `packId`。
- 触发：新安装、未配置文本模型，导入一篇已有文章，希望直接上传自己准备的封面和正文图。
- 影响：页面提示可以导入本地图片，但没有独立创建手动配图集合的路径。“没有生图模型仍可导入”的现有测试不等于“没有任何模型也能首次导入”。
- 优化：增加“直接导入图片”，在本地创建手动集合；资产可直接属于文章，AI 方案作为可选信息。封面与文内图可以指定用途、排序和插入位置。
- 验收：零模型配置完成文章导入、本地图插入、排版和 HTML 导出。

### F06 · P2 · 文章搜索和账号筛选存在状态不一致

- 搜索证据：`workflow-repository.ts:126` 对全文搜索并计数，`ArticlesPage.tsx:137` 对返回结果再做标题过滤。关键词只出现在正文时，后端计数有结果，列表却隐藏了该文章；分页也可能出现看似空白的结果页。定向实验已复现计数为 1、标题过滤后为 0。
- 账号证据：`ArticlesPage.tsx:111` 的查询 effect 不依赖 `currentAccountId`，但 `refresh` 查询使用该值。在“当前账号”模式下通过顶部切换账号，后台查询不会随之重跑，前端却会按新账号过滤旧列表。
- 优化：确定搜索究竟是标题还是全文，由服务端统一筛选与计数；取消分页结果的重复过滤。把账号纳入查询 key，切换时重置页码。可以同时增加输入防抖，避免每个字符都重读素材和框架。
- 验收：标题、正文关键词和无结果场景的列表与计数一致；A/B 账号连续切换无需离开页面就得到正确列表。

### F07 · P2 · 超过 500 篇后旧文章无法正常进入下游

- 证据：评审、配图、排版、发布页面分别固定调用 `articles.listSummaries({ limit: 500 })`，没有在目标 ID 不在列表时单独加载正文摘要。后端也将 limit 上限限制在 500。
- 触发：第 501 篇及更旧的文章，从正文工作栏跳转评审、配图或排版。
- 影响：目标文章虽真实存在，却无法从下游本地数组中解析，可能出现空选择或回退到别的文章。尤其发布页的排版集合与文章集合边界并不一致。
- 优化：选择器采用服务端分页搜索；路由指定的文章按 ID 独立读取并补入当前选项，明确区分目标已删除与目标不在当前页。
- 验收：准备 501 篇以上的数据，从最旧文章进入各阶段，始终保持正确标题、ID 和版本。

### F08 · P2 · 推送结果“待确认”缺少核对后的完整出口

- 证据：`wechat-publish-service.ts:97` 禁止 unknown 记录重试，这是合理的防重复保护；但 `PublishingPage.tsx:203` 对 unknown 只提供后台入口和正式发布链接登记。`ipc-publishing.ts:33` 对外更新只允许标记 published。
- 触发：请求发出后网络断开。用户到后台核对，发现草稿已经收到但尚未发布，或者明确没收到。
- 影响：不能把记录校正为“已收到草稿”或“已确认未收到”；直接重新推送新任务也无法清晰解释原记录与新记录的关系。
- 优化：增加核对操作并记录核对时间、依据与操作者；确认收到后绑定草稿标识，确认未收到后允许受控重试。继续保留 unknown 时禁止盲目重试的保护。
- 验收：成功但断网、发送失败、无法判断三类场景都有正确状态，且不会自动重复推送。

## 体验与产品能力建议

### F09 · 建议 · 减少重复导航，让正文成为首屏主体

实际 Electron 截图见 `artifacts/workflow-smoke/restart-debug.png`：左侧模块导航、顶部当前作品阶段栏、中间完整流程条同时展示。标题、新建草稿区和多行工具又占据编辑器上方，正文起点落在窗口较低位置。

建议保留左侧全局导航和紧凑作品栏，进入具体作品后折叠全流程条；新建参数放在抽屉；正文页提供专注模式、可收起文章列表、编辑/双栏/预览三种布局。对普通公众号作者，将“源码编辑”改为“编辑正文”，Markdown 技术说明放在帮助中。

验收时使用 1366×768 和系统缩放场景，重点观察不滚动时能读写多少正文、保存状态是否始终可见。无需为了视觉统一推翻现有首页多入口。

### F10 · 建议 · 事实评审必须区分“发现疑点”和“核实完成”

`review-service.ts:81` 的角色输入只有文章正文，没有关联素材和外部核验结果；`:145` 解析的问题默认 `adopted: true`。已有“事实核查”角色适合提出疑点，但这并不能证明某个数字或引文已被核实。

建议给事实类问题增加原文片段、来源链接、证据摘录和核实状态。默认不采纳会改变数字、引用和事实结论的建议；应用前显示 diff。可先做人工证据确认，再考虑外部检索自动化，避免另一个模型生成的断言被当作证据。

### F11 · 建议 · 将本地恢复副本升级为可带走的备份

`workspace-service.ts` 默认写入 `userData/backups`，备份与恢复路径被限定在数据目录中；`DataPage.tsx` 只有立即备份和列表恢复，没有用户选择外部位置导入导出的流程。对误操作回滚有价值，但与原数据在同一目录的副本不能应对整盘故障或数据目录被整体删除。

建议保留快速本地副本，同时增加系统文件选择器授权的备份包导出/导入、最近成功备份时间和提醒。换电脑后密钥能否解密需单独处理，提示重新配置密钥，不能把同机恢复成功当作跨设备密钥迁移成功。

### F12 · 建议 · 长素材展示实际入模范围，并控制整体上下文预算

文件导入服务只保留前 20000 字符；框架生成又对每条素材只取前 8000 字符，见 `file-material-service.ts` 与 `framework-generator.ts:169`。截断标记保存在内容中，但没有在生成决策处清楚告诉用户被省略了什么。正文生成则直接拼接所选素材，缺少总输入预算。

建议显示原文长度、保留范围和模型可用预算；按章节分块并根据主题选择片段，保留页码/段落位置。超限时让用户缩小范围或选择摘要，而不是靠前缀截断决定哪些事实进入模型。

验收：将关键结论放在文档后半部分，系统能找到该结论，或者明确告知它未被用于生成。

## 代码与验证体系优化

1. **用业务类型明确行为。** F02 表明数量参数同时承担写入策略会形成隐含耦合；F08 表明记录状态已有定义但状态转换没有完整设计。将“用户意图”和“执行参数”分开，再由集中服务执行状态转换。
2. **按功能边界逐步拆分。** 当前 `database.ts` 2395 行、`AccountPage.tsx` 1404 行、`HotspotsPage.tsx` 1280 行、`pages.css` 4156 行。行数本身不是缺陷，但与筛选、选中态和刷新逻辑重复结合后，维护风险明显。优先提取文章查询/选择、provider 表单状态、发布状态转换；数据库按账号、素材、文章、交付拆 repository，保留事务协调。不要一次全量重写。
3. **摘要查询应真正轻量。** `workflow-repository.ts` 的摘要查询仍返回完整 `rawMarkdown`，下游一次读取 500 篇正文，并伴随全量排版/素材读取。逐步让列表只拿标题、状态、版本和摘要，选中文章再读正文。此处是负载风险判断，未测出具体内存或延迟数字。
4. **保留已有安全基础。** 主窗口的 context isolation、关闭 nodeIntegration、sandbox、禁止导航，以及密钥使用 safeStorage、IPC 的 Zod 校验是正确方向。本次未证实需要紧急修复的安全漏洞，但这不代表完成全面安全认证。
5. **修复桌面回归覆盖断点。** 先修 F01，再重跑 articles/reviews；将 layouts 的文章定位改为精确匹配，再跑其完整流程。新增“补失败候选不改原稿”“length 结果不报完成”“501 篇目标直达”“无 AI 首次导入图片”等行为断言。本次缺陷复现实验需要在修复时反转为期望正确行为的回归测试。

## 建议实施顺序

- 第一批：F01 配置保存、F02 改稿重试、F03 截断结果、F04 图文复制；修通现有桌面回归。
- 第二批：F05 无 AI 图片流程、F06 搜索与账号过滤、F07 大文章库、F08 推送核对闭环。
- 第三批：F09 写作空间、F10 证据评审、F11 可携带备份、F12 长素材处理。结合真实作者试用数据确定先后。

最有价值的交付验收场景：第一次安装后，用户不接 AI 也能导入一篇文章和自己的图片，完成排版并可靠导出；接入 AI 后，生成失败、部分成功和中途改稿都不会误改原稿；推送结果不确定时，用户知道如何核对并继续。
