## P0 ✅ 修正文图片丢失（已交付）

### 问题

微信 `draft/add` 会主动过滤非微信图床的图片。项目从未调用 `media/uploadimg`，排版稿里的 `moliu-asset://` 是本机协议，**任何带图文章推到草稿箱，图片 100% 丢失**。

隐蔽性高：排版预览里图片正常显示（本机协议可访问），只有推到微信才消失，用户难以归因到软件。

### 已完成的修改

`src/main/services/wechat-publish-service.ts`（+127 行）：

| 新增 | 说明 |
| --- | --- |
| `uploadInlineImages()` | 遍历 `layout.html` 的 `<img src="moliu-asset://...">`，去重后逐个上传，全部成功后替换为微信图床 URL |
| `uploadInlineImageFile()` | 调 `cgi-bin/media/uploadimg`，含token 过期重试与 jpg/png 格式白名单 |
| `decodeAssetUrl()` | `moliu-asset://assets/<encoded>` → 文件名，与 `database.visualAssetUrl` 编码规则对应 |
| 字段长度校验 | title ≤32 字、digest ≤128 字、content ≤20000 字符，超限给中文原因而非微信错误码 |

**失败处理策略**：单张图失败不阻断整篇，但**必须明确告知哪些图没上传及原因**——否则用户看到的仍是"文字都在、图没了"，且无从排查。

**关键约束（已写入代码注释）**：

| 用途 | 接口 | 返回 |
| --- | --- | --- |
| 正文插图 | `cgi-bin/media/uploadimg` | 图床 URL，放`content` |
| 封面素材 | `cgi-bin/material/add_material?type=image` | `media_id`，填 `thumb_media_id` |

**用错接口拿到的 URL 放进正文，图片同样被过滤。**

### 测试

`tests/wechat-inline-image.test.ts`（7 例）：中文名还原、空格/特殊字符、非本机协议拒绝、残缺地址不抛错、路径穿越阻断、扁平存储约定。

> 写测试时发现一个设计约束：图片是**扁平存储**（`readAssetFile` 内部也走 `basename`），所以 `decodeAssetUrl` 必须只取文件名。我最初的测试期望写错了，代码是对的——已在两处都写明这个约束。

**回归**：typecheck 通过 · 全量测试 19 文件 123 例全绿（原 116 + 新增 7）

## P1 排版合规校验器（✅ 已交付）

### 为什么优先

平台限制现在**散落在 juice 配置和正则里**，没有一处能"确定性验证产物是否合规"。这导致：

- 改主题时可能悄悄引入违规写法，无人发现
- 用户看到"格式在微信里丢了"，但不知道原因

### 先修两个已验证的真实问题

我用 juice 实测了当前输出（`tests` 外的独立验证），结果：

| 检查项 | 实测结果 | 风险 |
| --- | --- | --- |
| `.hljs-keyword` 转内联色 | ✅ juice 成功转换 | 无（高亮不会丢） |
| `class` 属性 | ⚠️ **仍被保留** | 微信会过滤，虽不影响当前样式但属冗余 |
| `<div>` | ✅ 无 | 无 |
| **`<pre>`** | ⚠️ **保留** | **不在微信 37 标签白名单内，代码块可能整块散架** |
| `<table>` | ✅ 保留 | 无 |

**`<pre>` 是比"缺组件"更严重的问题**——技术类内容一旦发出去，代码块结构可能整个丢失。

### 方案

新增 `src/main/services/layout-validator.ts`：

```ts
export interface LayoutViolation {
  level: 'error' | 'warn'
  rule: string
  message: string
  hint?: string
}

export function validateWechatLayout(input: {
  html: string
  title: string
  digest?: string
}): LayoutViolation[]
```

**校验规则**（依据微信官方答复 + 多个实战来源交叉验证）：

| 规则 | 级别 | 依据 |
| --- | --- | --- |
| 无 `<div>` / `<script>` | error | 微信白名单约 37 标签 |
| 无 `class` / `id` 属性 | warn | 强制移除非内联属性 |
| 无 `position:fixed/absolute/sticky`、`float`、`display:grid` | error | 官方过滤清单 |
| **代码块不得用 `<pre>`** | error | 不在白名单，需转`<section>` |
| 所有文字被 `<span leaf="">` 包裹 | warn | 微信正文渲染依赖 |
| 图片 `src` 须为 `mmbiz.qpic.cn` 或占位 | error | 外链被过滤 |
| 图片用 `max-width:100%` 而非 `width:100%` | warn | 小图会被拉伸 |
| 无 `white-space:pre` | error | 会渲染出大段空白 |
| `title` ≤32 字 / `digest` ≤128 字 | error | draft/add 字段限制 |
| 无半角标点（代码块外） | warn | 中文排版规范 |

**接入时机**：`create()` 生成排版稿时 + `pushDraft()` 推送前各跑一次。有 error 时在界面上明确列出原因，而不是让用户去猜。

### 顺带做的修复

| 问题 | 修法 |
| --- | --- |
| `<pre>` 不合规 | 在 `renderLayoutMarkdown` 里把代码块渲染为 `<section>` + 每行 `<p style="margin:0">`；缩进用全角空格 `　`，**不用 `white-space:pre`** |
| `class` 冗余 | 内联完成后剥掉 `class`/`id`（样式已内联，留着无用） |
| 补 `<span leaf="">` | 文字节点统一包裹，提升在微信里的渲染稳定性 |
| 图片宽度 | 显式加 `max-width:100%;height:auto`，避免微信强制 `width:100%` 拉伸小图 |

**工作量**：约 1 天（含测试）

| --- | --- |

### 实施中发现并修正的 3 个问题

**1. `<pre>` 只是去掉 class 不够**
最初以为改掉 highlight 返回值即可，实测发现 markdown-it 会把返回值塞进 `<pre><code>`，外层 `<pre>` 仍在。必须用 `md.renderer.rules.fence` 彻底接管。

**2. 校验器自身有 bug（误伤 max-width）**
用子串匹配 `width:100%` 会把 `max-width:100%`（正确写法）一起拦掉。改为提取 style 值后逐条声明判断。**这正是"检测器要先证明自己靠谱"的又一例证**。

**3. 既有测试断言需要更新（非回归）**
`<strong>重点</strong>` 变成 `<strong><span leaf="">重点</span></strong>`——这是微信要求的正确形态，不是功能退化。已更新断言并注明原因。

- 4 类真实文章排版后**全部 0 error**（端到端，非构造样本）
- 自定义 CSS 引入 `position:fixed` 会被拦住（防止用户自定义绕过校验）
- typecheck 通过 ·构建通过 · 导航一致性✓ · 流程 13 项 ✓

### 实现的组件语法约定

参照调研发现，组件靠 Markdown 语法映射。**我们不需要发明语法**——用最容易被 AI 正确生成的写法：

| Markdown 输入 | 输出组件 |
| --- | --- |
| `> **引用文字**` | 金句块 |
| `::: tip 提示内容` | 提示块（`tip`/`warn`/`key`） |
| `[[toc]]` | 目录 |
| `---` （前后有空行） | 分割线变体 |
| `1. / 2. / 3.` 有序列表 | 序号药丸 |
| 首段前 3 行 | 引言卡（自动提炼） |
| `> 引述`（无加粗） | 旁注块 |

**关键设计决策**：组件必须**由 AI 可确定性生成**，且**降级友好**（不支持时退回基础样式，不报错）。

### 视觉规范（从调研提炼）

| 规范 | 数值 | 理由 |
| --- | --- | --- |
| 主色使用上限 | 全文 ≤5 处 | 彩色的功能是标重点，不是承载正文 |
| 灰阶承重 | 约 90% 文字走中性灰阶 | 避免花哨，保证长文可读 |
| 强调形式 | 左竖条 / 药丸标签 | 虚线框笨重抢戏，仅用于"待补素材" |
| 圆角 | 统一 6-8px | 视觉一致 |
| 字号阶梯 | 15/ 16 / 17 / 19 / 22px | 层级清晰 |
| 行高 | 正文 1.75-1.8 | 中文长文阅读舒适 |

**这几条正好呼应本轮可读性整改**——彩色的功能是标重点，不是承载正文。

### 组件语法

| 输入 | 输出 | 说明 |
| --- | --- | --- |
| `::: lead 内容` | 引言卡 | 开篇核心判断 |
| `::: tip 内容` | 提示块「提示」 | 补充说明 |
| `::: warn 内容` | 提示块「注意」 | 风险提醒 |
| `::: key 内容` | 提示块「重点」 | 关键结论 |
| `::: note 内容` | 提示块「旁注」 | 引用旁证 |
| `[[toc]]` | 目录 | 自动汇总二三级标题；标题不足 3 个时不生成 |
| `---` | 装饰分割线 | 替代默认 hr |

### 三条实现原则

1. **语法要对 AI 可确定性生成** —— 不用需要嵌套或参数的复杂语法，避免模型写出半个语法导致失败。
2. **降级友好** —— 未闭合的 `:::` 会被当作普通文本而非报错。一篇文章因一个符号渲染不出来是灾难。
3. **不用虚线框做强调** —— 四周虚线框笨重抢戏，只留给「待补素材」占位。强调一律用左竖条或药丸标签。

### 实施中踩的 3 个坑

**1. 自定义 HTML 标签会被转义**
markdown-it 配置了 `html: false`，`<mly-callout>` 会被转义成文本。改用**占位段落**方案：先转成带唯一 id 的 `<p>`，渲染后按 id 精确回填。

**2. 多行正则有歧义，改用逐行扫描**
`^::: *(tip|...)
([\s\S]*?)
:::[ 	]*$` 配合 `m` 标志在多行块上匹配失败（实测 slots=0）。改成逐行扫描找闭标签，逻辑更直观也更好维护。

**3. 组件语法要同时支持两种写法**
`::: tip 内容`（同行）与 `::: tip\n内容\n:::`（换行）都常见，第一版只支持换行导致提示标签与内容被拆成两行。

### 视觉规范落地

| 规范 | 落地方式 |
| --- | --- |
| 主色只在锚点出现 | 组件主色来自主题 accent，正文仍用主题 text 色 |
| 不用虚线框做强调 | 全部用左竖条（4px）或药丸标签 |
| 约九成文字走灰阶 | 提示块正文用 `#595959`，标题与强调才用彩色 |
| 圆角统一 6-8px | 组件统一 `border-radius: 0 8px 8px 0` |

## P3 主题体系升级（✅ 已交付）

### 现状问题

我们有 5 套主题（`wechat-green` / `magazine` / `tech-blue` / `warm-paper` / `minimal`），但**只有 CSS，没有元信息**。用户面对 5 个色块盲选，不知道哪个适合自己的文章。

### 借鉴「配方表」思想

调研项目的主题不只是一堆 CSS，每套都带五章节结构：

```
1. 设计变量表   —— 主色/浅底/深字/灰阶/圆角/字号阶梯
2. 组件清单     —— 该主题下的组件样式
3. 骨架         —— 文章整体结构
4. 配方表       —— 按文章类型推荐组件组合
5. 映射表       —— Markdown 元素 → 组件的映射
```

**其中"配方表"最有价值**——它把"选主题"变成"选文章类型"。

### 方案

**（1）给每个主题补元信息**

```ts
export interface LayoutThemeMeta {
  id: string
  name: string
  /** 主色（用于 UI 展示） */
  accent: string
  /** 适合的文章类型 —— 用户据此选择，而非盲选色块 */
  suitedFor: string[]
  /** 该主题的视觉性格，一句话 */
  personality: string
}
```

推荐配置：

| 主题 | 适合 | 性格 |
| --- | --- | --- |
| 摸鱼绿（现 wechat-green） | 教程、测评、清单、工具盘点 | 清晰、友好 |
| 红白（新增） | 深度分析、观点、力量感话题 | 强烈、有力 |
| 石墨极简（现 minimal） | 设计、科技评论、专业观点 | 克制、专业 |
| 留白禅意（新增） | 深度随笔、感悟类 | 安静、留白 |
| 暖纸（现 warm-paper） | 叙事、故事、人物 | 温和、亲近 |
| 杂志（现 magazine） | 长文、深度报告 | 精致、编排感 |
| 科技蓝（现 tech-blue） | 技术教程、代码 | 清晰、理性 |

**（2）界面上让用户按"文章类型"选主题**，而不是按颜色。

**（3）主题生成器**（可选，延后）让用户用一句话或一张参考图生成新主题。这是调研项目最受欢迎的功能，但工作量大，建议 P3 之后再看。

```
         已按「教程攻略」推荐此主题：清晰友好，最不容易出错的选择
```

**关键设计**：把"选色块"变成"选内容类型"。用户不需要懂排版术语，只需要知道自己要写什么。

### 实施中踩的 2 个坑

**1. mock-bridge 与真实 preload 不同步（值得警惕）**
新增 `layouts:genres` 后没同步 mock，导致浏览器预览时 `window.moliu.layouts.genres is not a function`，
**被 ErrorBoundary 捕获后整页不可用**。而且 mock 原本 `themes()` 返回空数组，主题下拉本来就没数据。

教训：**新增任何 preload 接口都要同步 mock**，否则浏览器环境会静默崩溃。建议在 mock-bridge 里补一条接口齐全性断言。

**2. 浏览器 mock 环境无法验证需要数据的界面**
排版页在无文章时显示空态，composer 根本不渲染，选择器自然找不到。改用真实 Electron + 先造一篇文章才验通。

### 验证结果

- 15 例单测：元信息完整性、suitedFor 合法性、推荐结果必定适配、无孤儿主题、推荐确定性
- 真实Electron 界面验证：选「教程/攻略」→ 自动切到「微信经典」+ 显示推荐理由
- 全量 **24 文件 209 例全绿** · typecheck ✓ · 导航 ✓ · 流程 13 项 ✓

### 未做（有意延后）

- **配方表**（按文章类型推荐组件组合）：需要先积累真实使用数据，现在做会凭空设计
- **主题生成器**（一句话/参考图生成新主题）：调研项目最受欢迎的功能，但工作量大，建议 P4 之后评估

## P4 表格与公式（体制内内容刚需）

### 为什么优先级不低

如果坚持"体制内考试"这个定位：

| 内容类型 | 表格/公式需求 |
| --- | --- |
| 岗位表、职位表 | 表格刚需 |
| 数量关系（数学题） | **公式刚需** |
| 资料分析（数据题） | 表格 + 百分比 |
| 逻辑判断 | 表格辅助 |

**这两项不是"锦上添花"，是内容能不能正常发布的问题。**

### 表格

我们已有基础样式（斑马纹 + 边框），需要补：

| 改进 | 理由 |
| --- | --- |
| 表头吸顶效果不可用 | 微信不支持 `position:sticky` |
| 窄屏横向滚动 | 微信里宽表格会溢出屏幕 |
| 单元格内文字换行 | 现在的实现长文本会撑破 |
| 数字列右对齐 | 数据可读性 |

### 公式

引入 **KaTeX**（`katex` + `markdown-it-katex` 或 `@vscode/markdown-it-katex`）。

⚠️ **微信兼容是难点**：KaTeX 输出大量 `<span>` + CSS 变量 + `position:absolute`（用于大括号/根号），这些在微信里**几乎必然被过滤**。

**可行的替代方案**：

| 方案 | 效果 | 成本 |
| --- | --- | --- |
| KaTeX 转成图片 | 清晰可靠，但公式不可复制、SEO 差 | 低 |
| KaTeX 输出后做微信兼容改写 | 保留文本形式，部分符号可能错位 | 高 |
| 只支持行内简单公式 | 覆盖大部分需求 | 中 |

**建议**：先做「KaTeX 渲染后转图片」，成本低、效果确定。复杂公式布局的兼容性改造留到有真实需求时。

**工作量**：表格 1 天 + 公式 1 天

## P5 排版实时预览 —— 建议不做

调研中有项目提供实时预览（编辑区 + 预览区并排 + 手机预览）。

**我们不建议做**，理由：

| 论据 | 说明 |
| --- | --- |
| 我们的差异化不在编辑器 | 用户已有 Typora/Obsidian 写 Markdown，我们的价值是"写完直接发" |
| 成本极高 | 要做所见即所得、撤销重做、移动端预览，是另一个产品 |
| 已有替代 | 排版稿本身就是可预览的（存库了），用户可以反复生成不同主题对比 |
| 会分散精力 | 排版组件 + 合规校验的投入产出比高得多 |

如果用户强烈反馈需要预览，**先做轻量版**：排版稿页面加一个"用其他主题重排"的按钮 + 主题切换预览，1 天可上线。

## 执行顺序与依赖

```
P0 ✅ 正文图上传（已交付）
      │
      ▼
P1 合规校验器 ──┬── 顺带修 pre → section、剥 class、补 span leaf
                │   （这些是"能正确发出去"的前提）
                ▼
P2 版式组件库  ←── 依赖 P1 的校验规则（组件也要过校验）
      │
      ├──────► P3 主题元信息（组件要按主题换色）
      │
      ▼
P4 表格与公式
```

**P1 必须先于 P2**：新组件上线时如果不能过校验，就会出现"新增一种格式丢失方式"。

## 风险与取舍

| 风险 | 应对 |
| --- | --- |
| 组件过多导致排版变花哨 | 严守"主色 ≤5 处、90% 灰阶"；组件默认不开启，按需用 |
| 微信平台规则变化 | 校验规则集中在 `layout-validator.ts`，一处更新 |
| KaTeX 兼容性 | 先走转图片方案，不投入改造 |
| 主题元信息成为维护负担 | 只补 5-7 套稳定主题，不追求数量 |
