## 一句话结论

**公众号排版的本质是"一条极窄的白名单 + 只认内联样式"，专业平台保真靠的不是玄学，而是三件事：①只输出白名单内的 section/span + 全内联样式；②在"公众号同款渲染环境"（375px 宽、微信基础样式、暗黑模式）里做预览；③用官方校验工具或大量实测把每条 CSS 属性验证过。我们现在三个都已有雏形，缺口集中在"预览环境模拟"和"对齐官方结构规范"。**

> 本次调研最重要的发现：**微信官方开源了一套图文结构校验工具（MIT 协议）+ 一份权威规则文档**，可直接接入我们的校验链路。详见 §2.4。

## 第一部分：公众号排版的原理（官方事实）

### 1.1 内容进公众号的三条通道

任何"排版"最终都要走这三条路之一，三条路的过滤规则趋同：

```
通道 A：网页编辑器「粘贴」
  复制方写入剪贴板 text/html → mp 后台编辑器接收 → 前端 sanitizer 清洗 → 存草稿
通道 B：API「新建草稿」draft/add（我们当前的方式）
  content 字段 HTML → 微信服务端清洗 → 存草稿
通道 C：第三方「同步」/浏览器扩展（秀米、135、壹伴等）
  ① 绑定公众号授权 → 服务端调 draft/add（本质还是通道 B）
  ② 扩展直接注入编辑器 DOM（本质是绕过剪贴板的通道 A）
  ③ SVG 交互等剪贴板带不走的内容，必须走服务端同步
```

**关键认知：不存在"不过滤"的通道。** 无论哪条路，微信都会把内容清洗成"白名单标签 + 内联样式"的安全子集。专业平台和我们的差别不在于绕过过滤，而在于**生成的内容从一开始就只含白名单成分**。

### 1.2 官方文档明确的硬规则（draft/add，已核验官方文档原文）

来源：[新增草稿接口官方文档](https://developers.weixin.qq.com/doc/subscription/api/draftbox/draftmanage/api_draft_add.html)（2026-07-14 更新）

| 字段 | 官方规则 |
| --- | --- |
| `content` | 支持 HTML 标签；**少于 2 万字符且 < 1M**；**会去除 JS**；**图片 url 必须来自「上传图文消息内的图片获取URL」接口（uploadimg），外部图片 url 将被过滤** |
| `title` | ≤ 32 字 |
| `author` | ≤ 16 字 |
| `digest` | **≤ 120 字**（2026-07 起与 mp 端对齐；⚠️ 我们 layout-validator.ts 里写的 128 需要改成 120） |
| `content_source_url` | ≤ 1 kb（阅读原文链接） |
| `thumb_media_id` | 必须是永久 MediaID |

两个注记：
- 官方文档 content 描述里有一句"大小不可超过2kb"，与"2万字符/1M"矛盾，应是文档笔误，以 2 万字符/1M 为准（多篇实战资料一致）。
- `<a>` 标签：[uploadnews 官方文档](https://developers.weixin.qq.com/doc/subscription/api/notify/message/api_uploadnewsmsg.html) 明确"具备微信支付权限的公众号可使用 `<a>` 标签，其他公众号不能使用"。普通账号的外链应转文末脚注（开源工具的通行做法，见 §3.4）。

**官方从未公开完整的标签白名单。** draft/add 文档只说"支持 HTML 标签、去除 JS"。社区通过实测反推的黑名单/白名单（多个独立来源交叉验证一致）：

| 分类 | 内容 | 处理方式 |
| --- | --- | --- |
| 必然被删 | `script` / `style` 标签、`iframe` / `object` / `embed` / `form` / `input` | 整体移除 |
| 不支持 | `<div>`（**实测确认会被直接移除**，连带内部内容散架）、`<pre>` 包正文（窄屏截断） | 移除/散架 |
| 推荐用 | `section` / `p` / `span` / `strong` / `em` / `b` / `i` / `u` / `br` / `ul` / `ol` / `li` / `blockquote` / `table` / `thead` / `tbody` / `tr` / `td` / `th` / `img` / `h1`~`h6`（弱支持，建议用 section 自己做标题） | 保留 |
| 微信专属 | `mpvoice`（音频）/ `mpvideo`（视频）替代 HTML5 标签；`<a>` 仅限微信支付权限账号 | 保留 |
| 属性 | **`class` / `id` 全部剥离**（连 SVG 内的 id 都会剥）；事件属性（onclick）全删 | 剥离 |
| 样式 | 只保留**内联 style 属性**，且仅白名单属性；`<style>` 标签、外部 CSS、伪类、`@media`、`@keyframes` 全部无效 | 过滤 |

### 1.3 CSS 支持清单（社区实测综合）

来源：[Axton Liu《微信公众号图文的 HTML/CSS 支持概览》(2025-03)](https://www.axtonliu.ai/newsletters/ai-2/posts/wechat-article-html-css-support)、[bm.md 实现解析](https://www.verysmallwoods.com/blog/20260119-wechat-markdown-copy-paste) 等多个独立来源交叉验证。

**可靠支持**（全部以 px 为单位最稳）：
- 文字：`color` `font-size` `font-weight` `font-style` `letter-spacing` `text-align` `text-decoration` `line-height` `vertical-align`
- 盒子：`margin` `padding` `border` `border-radius` `box-shadow` `max-width`
- 背景：`background-color`；`linear-gradient` 可内联但有暗黑模式风险（见 §1.4）
- 布局：`display`（block / inline-block / flex 基本可用，grid 不行）
- 装饰：`opacity` `overflow`（hidden/auto 用于代码块滚动）

**不可用 / 高风险**：
- `position: absolute/fixed/sticky`（被删，z-index 随之无效）
- `float`（不被禁但极易破坏布局，勿用）
- `display: grid`（被过滤）
- `transform` / `animation` / `transition`（被过滤；简单 transform 近期有部分生效的实测报告，但不可依赖）
- `:hover` 等伪类、`@media`、`@keyframes`、CSS 变量 `var(--…)`、`@font-face` 外部字体
- 百分比单位不稳定（如 `margin-top: -100%` 无效），**统一用 px**
- 表单元素全不支持（任务列表复选框 → 用 ☑ / ☐ Unicode 字符替代）

**经验法则（bm.md 总结，很精辟）：如果一个 CSS 效果需要 JavaScript 或 `<style>` 标签才能实现，它在微信里大概率不行。**

### 1.4 官方《编辑器插件开发规范》——最权威的结构规则（本次新发现）

来源：[微信公众平台编辑器插件开发规范（官方文档，2026-08-26 版）](https://developers.weixin.qq.com/doc/service/guide/product/plugin_spec.html)

这份文档是微信对第三方排版插件（135/秀米类工具方）的正式约束，**等于官方承认的"什么内容会被编辑器自动删除"**：

| 规则 | 原文要点 |
| --- | --- |
| 嵌套层级 | 同一标签名 + 同一内联样式 + 仅含单个子节点的连续嵌套链**不超过 10 层**，超出"编辑器会自动精简冗余的嵌套层级"（结构规范中阈值为 15 层起检） |
| `span[leaf]` | 行内容器，**只能含行内元素（span/strong/img 等）或文本，严禁包裹 section/div/p 等块级元素** |
| `section[nodeleaf]` | 只能包官方指定组件或 img |
| `line-height` | **不能小于字号**，否则多行叠字（豁免：图片无缝拼接、实际单行） |
| `width` | 固定宽度导致居中不一致/溢出/比例不一致三类问题；**img 建议带 `data-w` 属性**（原始像素宽）；可用 `data-ignore-width` 豁免横向滚动容器、视觉裁剪特效 |
| `height` | height:0 容器含文字在移动端完全不可见；固定高度内容溢出被裁剪（可滚动容器豁免） |
| `text-align` | 禁用 `start/end` 值（终端兼容差异） |
| `<pre>` | 不得包普通正文；代码块需 `overflow-x: auto/scroll` |
| `caret-color` | 不得全透明；`img` 不得 `opacity:0` 再叠 SVG 背景（发布后无法改图） |
| **字体** | **不建议设置任何 font-family**，用官方默认字体栈（mp-quote, PingFang SC, system-ui…）；自设字体在 iOS 17+ 会有字号/字距渲染差异 |
| SVG 动画 | `animate` 的 begin 应写 `begin="touchstart; click"`（只写 touchstart 则 PC 端不触发） |
| **暗黑模式** | 检测文字/背景对比度；文字背景避免渐变（会被转纯色）；背景写在公共容器而非逐个文本节点；**禁止绝对定位破坏视觉与结构顺序**；SVG 用 `fill="currentColor" stroke="currentColor"` 避免黑底黑字；**任何场景不要用 `!important`** |
| 豁免属性 | `data-no-dark`（跳过暗黑转换）、`data-ignore-dm="low-contrast text-bg-gradient"`、`data-ignore-width` |

### 1.5 官方开源校验工具（本次最重要发现）

来源：[wechatjs/verify-article-structure-spec](https://github.com/wechatjs/verify-article-structure-spec)（**微信官方 wechatjs 组织，MIT 协议**）

- **权威规则文档** `verify_article_structure.md`：上述所有规则的编号定义、阈值、判定逻辑、豁免机制
- **CLI**（`npm run check ./article.html --json`）：基于 **puppeteer 真实浏览器渲染**检测——能测出"width 实际溢出""line-height 实际叠字""height 溢出裁剪"这类**静态正则测不出来**的问题
- **dedupe 命令**：自动清理冗余嵌套（检测→清理→复测闭环）
- 依赖 mp-darkmode 做暗黑模式校验；npm 包 `verify-article-structure` 已发公网 npm
- 注意：README 明示"CLI 检测通过并不代表已覆盖规范全部要求"（2.2/2.3/第 3 章字体等规则 CLI 尚未实现）

**对我们的意义：MIT 协议，闭源桌面应用可以合法集成。** 我们的 layout-validator.ts 是"正则静态断言"，官方 CLI 是"真实渲染断言"，两者互补。集成方式：主进程起一次 headless Chrome（Electron 自带 Chromium，可用 puppeteer-core 指向本机 Chrome 或 Electron 二进制），对排版稿跑 check，把 JSON 结果映射进现有 LayoutViolation 体系。

### 1.6 图片规则（已在 10-05 报告核验，此处汇总）

| 用途 | 接口 | 返回 | 备注 |
| --- | --- | --- | --- |
| 正文插图 | `cgi-bin/media/uploadimg` | 图床 URL（mmbiz.qpic.cn），可直接放 content | content 内外链图被过滤；微信对非微信域名图有 Referer 防盗链 |
| 封面 | `cgi-bin/material/add_material?type=image` | media_id | 填 thumb_media_id，与正文接口不能混用 |

- `img` 要显式写宽度（`data-w` + style width），否则 iOS 可能不显示；微信会强制限制图片不超屏宽
- SVG 内 `<image>` 的 href 必须是微信素材库链接（外链、Base64 都不显示）；SVG 不能嵌套 SVG；`transform-origin` 内联在 iOS 上无效
- 复杂动效只能 GIF / SVG+SMIL（兼容性差），CSS 动画和 JS 一律不可用

### 1.7 渲染环境：为什么"预览里好看 ≠ 发出去好看"

正文在微信客户端的 webview 里渲染（iOS WKWebView / 安卓 X5 内核，PC 端另一套），要点：

1. **基础样式**：正文容器是 `#js_content`（`rich_media_content`），默认字号约 17px，且 UA 样式会给 `p` 等元素自带 margin。专业排版输出的做法是**每个元素都显式写 `margin:0;padding:0;` 重置 + 显式 font-size**，不给 UA 样式留发挥空间——这是"复制过去总差一点"的常见原因之一。
2. **没有 media query / hover**：自适应只能靠 vw/px 组合（居中布局建议用 margin: 0 auto + max-width）。
3. **暗黑模式**：微信会算法转换颜色（正文底色 #191919），主题必须考虑暗色下的对比度（§1.4 规则）。
4. **连续空格被合并**、代码 `\n` 可能失效（→ `<br>`）、首行缩进用 `\u00A0`（不可断空格不会被合并）——bm.md 的实测坑清单。
5. **宽度基准**：手机正文可视宽度约 375~414px（iPhone 标准 375），排版稿容器按此设计；官方规范里 width 检测阈值 677px（PC 编辑器宽度）。

### 1.8 归因：我们此前的复制效果为什么差于专业平台

结合以上规则与本项目代码现状（`article-layout-service.ts` 已有 juice 内联 + span leaf + fence 接管），"差距"大概率来自以下几项的组合：

| # | 差距点 | 专业平台做法 | 我们现状 |
| --- | --- | --- | --- |
| 1 | 预览环境 | 在编辑器同款环境（375px 宽、微信基础样式、暗色切换）里预览，所见即公众号所得 | 预览用的是自己的页面环境（宽度、UA 默认样式、字体栈都不同） |
| 2 | UA 重置 | 每个元素显式 margin/padding/font-size，不留 UA 样式空间 | 主题 CSS 只给部分元素写全重置（未逐元素覆盖） |
| 3 | 结构规范 | 按官方规范控制嵌套深度、leaf 语义、行高 ≥ 字号 | 未系统对齐（嵌套精简、line-height 下限、data-w 均无） |
| 4 | 校验 | 平台内部有多年实测积累的属性支持表；官方现在提供了校验工具 | layout-validator 为静态正则，缺"真实渲染"层 |
| 5 | 字体 | 不设 font-family，跟随官方默认栈 | 主题里设置了 font-family（iOS 17+ 有渲染差异风险） |

### 2.2 doocs/md：复制路线的标杆

机制（多来源交叉验证，含官方 README 与实现剖析文章）：

```
Markdown → 解析渲染 HTML → 套主题 CSS（scoped）
        → juice 把 CSS 全部内联进 style 属性   ← 核心
        → 写剪贴板（text/html + text/plain 双格式）
        → 用户粘贴进公众号编辑器
```

- **剪贴板双格式**：`e.clipboardData.setData('text/html', …)` + `setData('text/plain', …)`；或 `navigator.clipboard.write` + `ClipboardItem`（Blob type `text/html`）。双格式是必须的——不同目标应用对格式的优先选择不同。
- **图床 13 种**：GitHub、阿里云 OSS、腾讯云 COS、七牛、MinIO、S3 协议、Cloudflare R2、又拍、Telegram、Cloudinary、自定义上传、**微信公众号（uploadimg）**。他们同样把"传到微信图床"作为一等公民选项。
- **生态位**：Chrome/Firefox 扩展、uTools 插件、CLI（@doocs/md-cli）、Docker 自托管、AI 助手集成。
- 局限（对我们）：只到"复制"，不做 draft/add API 发布；主题是纯 CSS 无元信息体系。

### 2.3 mdnice：主题即"元素样式配置表"

- 主题不是一份大 CSS 文件，而是**按元素（h1/h2/p/blockquote/code/链接/表格…）组织的样式配置集合**，社区在 [product.mdnice.com/themes](https://product.mdnice.com/themes) 提交主题，官方精选上架。
- 这个形态的启示：**主题的最小单位是"元素级样式配方"而不是整页 CSS**，天然适配"AI 按配方装配"的路线（与 gzh-design 的组件配方表思想同源）。

### 2.4 bm.md：工程化最完整的公开管线

来源：[《公众号排版工具如何实现样式的复制粘贴？》](https://www.verysmallwoods.com/blog/20260119-wechat-markdown-copy-paste)

- **管线**：remark-parse → remark-gfm → remark-math → remark-rehype → rehype-highlight → **rehype-wechat-adaptor（平台适配器）** → rehype-stringify → `<section id="…">` 包裹 → `juice.inlineContent(html, themeCss)` → 剪贴板。
- **适配器模式**：微信/知乎/掘金共享核心渲染，各自 limitation 由 adaptor 收口。我们目前只有微信，但这个抽象为将来留了口。
- **Web Worker 渲染**：长文 Markdown 字符串/AST 操作卡主线程 → 全部挪进 Worker（oRPC 通信）。Electron 渲染进程同样适用。
- **实测坑清单**（§1.7 已引）：空格合并→`\u00A0`、代码换行→`<br>`、复选框→☑/☐、外链→文末脚注、IndexedDB 回退内存。
- **MCP 集成**：把 render/parse/lint 暴露成 MCP server 供 AI 调用——与我们"AI 排版"方向高度契合，lint 能力对 AI 尤其重要。

### 2.5 wxeditor / feishu2wx：预览与主题的终端形态

来源：[colobu《写公众号最痛苦的那段流程，终于有人重做了》](https://colobu.com/2026/04/26/reinventing-wechat-blog-writing-workflow)、[feishu2wx 作者博客](https://wangruofeng007.com/blog/2026-07/feishu2wx-intro)

- **默认按手机宽度预览**（贴近公众号真实阅读场景），需要时再切 1024px 网页模式——预览一致性从这里来。
- **主题 = 可导入导出的 JSON 配置**：自定义主题可保存/重命名/删除/分享；160 套 highlight.js 高亮主题实时切换；浅色/深色代码主题智能过滤。
- **标题装饰体系**：H2/H3/H4 支持 Unicode 前缀（✦ ➜ ◆ 【 ▍）+ SVG 装饰标题——低成本做出"设计感"的路线。
- **图片链路**：粘贴/拖拽上传 → 自动压缩 → 占位符持久化（IndexedDB）→ 复制时恢复。

### 2.6 商业平台的"保真"到底靠什么（拆解秀米/135/壹伴）

来源：[壹伴格式乱分析](https://yiban.io/geo/31887)、[135 编辑器对齐指南](https://www.135editor.com/geo/gongzhonghaobianjiqi/1347)、[秀米上传教程](https://www.cnblogs.com/MrFlySand/p/16817253.html) 等。

| 机制 | 说明 | 保真来源 |
| --- | --- | --- |
| 全内联样式生成 | 所有模板组件从源头就是 section/span + 全内联样式，无 class/style 标签 | 内容生来合规 |
| 浏览器扩展注入 | 壹伴/秀米插件直接操作 mp 编辑器 DOM，甚至提供"HTML 源码模式" | 在编辑器自己的环境里所见即所得 |
| 绑定公众号服务端同步 | 秀米/135"同步到公众号"：绑定授权后由服务端调草稿接口写入；SVG 交互等剪贴板带不走的内容**必须**走这条路 | 等价于我们的 draft/add 通道 |
| 多年实测的属性支持表 | 每个模板的每条 CSS 都在真机上验证过 | 工程积累 |

**结论：专业平台没有任何"魔法通道"。** 它们的保真 = ①内容生来合规 + ②编辑器同款环境预览 + ③（对 SVG）服务端同步。我们已有 ③（draft/add），要补 ①②。

## 第三部分：定制化前端版式体系的方案建议

### 3.1 目标管线（推荐架构）

```
写作内容（Markdown + 组件语法）
   ↓ markdown-it（fence 接管等，已有）
语义 HTML（scoped class）
   ↓ 主题 CSS（token 驱动，白名单属性约束，已有）
juice 全内联（已有）
   ↓ 微信兼容后处理（已有 span leaf；建议补齐 ↓）
  · 逐元素 margin/padding/font-size 重置（对齐 UA 样式）
  · img 补 data-w + 显式 width
  · 外链 → 文末脚注
  · 空格/换行修复（\u00A0、<br>）
  · 嵌套精简（对齐官方 dedupe 规则）
   ↓ 校验双关卡
  · layout-validator.ts（静态断言，升级对齐官方规则，见 3.4）
  · verify-article-structure CLI（真实渲染，MIT，可集成）
   ↓ 双出口
  · draft/add API 发布（已有，含 uploadimg 图链路）
  · 复制到剪贴板（Electron clipboard.write({ html, text })，双格式）
预览
  · iframe 固定 375px 宽 + 注入微信基础样式（js_content 模拟）+ 暗黑模式切换
```

### 3.2 主题系统设计（定制样式的核心）

三个层次的演进（从我们现状出发）：

**L1 现状（已有）**：5+ 套主题 = scoped CSS 字符串 + juice 内联。问题：只有颜色/字体变量，无元信息、无组件联动。

**L2 推荐形态（参考 mdnice 主题表 + gzh-design 配方表，10-05 报告 P2 已列）**：

```ts
interface LayoutTheme {
  // 元信息：选主题的人看"适合什么文章"，不再盲选色块
  meta: { name: string; genre: ArticleGenre[]; tone: '克制'|'活泼'|'专业'; darkModeSafe: boolean }
  // 设计 token：一处改，全文联动
  tokens: { accent: string; text: string; muted: string; bg: string; radius: string;
            headingFont?: never;  // ⚠️ 不再设 font-family，跟随官方默认栈（官方规范） }
  // 元素级配方（mdnice 形态）：h2/p/quote/strong… 的样式片段，含 margin/padding 全量重置
  elements: Record<'h2'|'h3'|'p'|'quote'|'strong'|'li'|'table'|'divider', (t: Tokens) => string>
  // 组件配方（gzh-design 思想）：引言卡/章节编号/金句/提示块/目录…
  components: Partial<Record<ComponentId, (t: Tokens) => string>>
  // 文章类型适配：教程类推荐哪些组件、叙事类推荐哪些（10-05 报告的 P2 项）
  recipes: Record<ArticleGenre, ComponentId[]>
}
```

**L3 定制化出口**：把主题导出为 JSON（wxeditor 的做法），支持用户自建/导入/分享主题；将来甚至可以让 AI 按"品牌色 + 文章类型"生成 tokens 与配方。

**约束写死在类型与 lint 里**（不让定制自由变成翻车自由）：
- 元素样式只允许白名单 CSS 属性（清单见 §1.3），layout-validator 兜底
- 每个元素配方必须显式包含 margin/padding 重置（模板级检查）
- line-height ≥ 字号；禁 `!important`；禁 font-family（仅系统字体栈可写不写都行）

### 3.3 预览保真方案（所见 = 公众号所得的关键）

这是"显示效果不如专业平台"的最大补强点：

1. **预览容器**：iframe 宽度锁定 375px（可切 414/桌面 1024 对照），背景模拟公众号正文白底。
2. **注入微信基础样式**：在预览 iframe 里注入一套 `#js_content` 模拟样式（默认字号 17px、UA margin 等），使排版稿里"没写全的重置"也会暴露出问题——预览越接近微信，遗漏越早暴露。
3. **暗黑模式切换**：预览可切暗色（底色 #191919），检查主题对比度（官方 4.1 规则）。
4. **终极对照**：发布到草稿箱后，提供"打开草稿箱预览"直达（公众号后台草稿可见手机效果）——把"回读草稿"纳入排版验收流程（10-05 报告已建议用草稿回读排查，这里是把它产品化）。

### 3.4 校验体系升级（自研 + 官方双关卡）

现有 `layout-validator.ts` 与官方规范的差异对照（本次调研直接产出）：

| 检查项 | 我们现状 | 官方规范要求 | 动作 |
| --- | --- | --- | --- |
| digest 字数 | ≤128 | **≤120**（2026-07 更新） | 改常量 |
| 嵌套层级 | 无检查 | 同名+同样式+单子节点 ≤10~15 层，超限被自动精简 | 补检查（或用官方 dedupe） |
| `span[leaf]` 内容 | 有包裹逻辑 | 只能含行内元素/文本，**禁包块级** | 补"leaf 内不含 section/p"检查 |
| `line-height` | 无检查 | ≥ 字号，否则移动端叠字 | 补检查 |
| `width`/溢出 | 无检查 | 固定宽度/大 margin 溢出；img 带 data-w | 补检查 + 输出时补 data-w |
| `height:0` | 无检查 | 含文字内容移动端不可见 | 补检查 |
| `text-align: start/end` | 无检查 | 禁用（终端差异） | 补检查 |
| font-family | 主题里在用 | **官方不建议设置**（iOS 17+ 差异） | 主题模板去掉（系统栈可保留为"不写"） |
| `!important` | warn | 官方明令不建议（破坏暗黑转换） | 保持 warn → 建议 error |
| 暗黑模式 | 无 | 对比度、渐变背景、currentColor | 先做主题侧约定，后接 mp-darkmode |
| 外链图 / 本地协议 | 已有 | mmbiz.qpic.cn | 已覆盖 ✓ |
| 标签黑名单 / class/id / 内联 | 已有 | 同 | 已覆盖 ✓ |
| **真实渲染级检测**（溢出/叠字/裁剪） | ❌ 静态正则做不到 | 官方 CLI 有 | **集成官方 CLI（MIT）** |

集成官方 CLI 的落地方式：`puppeteer-core` + 本机 Chromium/Electron 二进制跑 `verify-article-structure`（npm 包），把 JSON 结果映射为 LayoutViolation 展示；在"生成排版稿"与"推送草稿箱"两个时机复用。注意官方 README 声明 CLI 未覆盖全部规则（字体、leaf/nodeleaf 等仍需自研静态检查）——所以是**双关卡互补**，不是替代。

### 3.5 进阶方向（按需启用）

| 方向 | 要点 | 优先级 |

### A3. 落地方式修正（比正文 §3.4 更贴合 Electron 形态）

- **官方 verify CLI 不要进用户安装包**（puppeteer 依赖 Chromium 几百 MB，且用户机器未必有系统 Chrome）。推荐两种形态：
  - **开发期/CI 工具**：作为 devDependency + 校验脚本，在发布流程里跑 `npm run check`，把违规在开发期拦住；
  - **应用内轻量自研**：A2-6 的静态规则补齐后，用 Electron 自带 `webContents` 离屏渲染排版稿（约 200 行），把"真实渲染溢出/叠字"两项最关键的检测自己做掉——不必引 puppeteer。
- **doocs/md star 数修正**：以仓库页直读为准 **13.5k★**（部分旧文章写 9.2k）。

### A4. 需要警惕的"反例"

- **华生编辑器（huasheng_editor, MIT）在输出里加 `!important`**：与官方规范"任何场景不建议 `!important`"直接冲突（破坏暗黑模式算法与公共样式覆盖）。MIT 虽可用代码，**这条做法不要学**。
- 华生"图片转 Base64 复制"利用的是**粘贴通道**特性（mp 编辑器粘贴时可能自动转存图床；社区实践声称，未实测）——**API 通道（draft/add）不适用**，我们两条通道都要走，不能依赖它。
- **md2wechat-lite（MIT CLI）**：转换依赖云端 API Key（md2wechat.app），非纯本地引擎，不能当离线转换参考。

### B4. 盘点后的两个趋势判断

1. **MCP/AI 化是当前最活跃的演进方向**：wenyan-mcp、md2wechat-mcp-server、wechat-publisher-mcp、gzh-design-skill（Skill 形态）——公众号 API 正在被包装成 AI 工具层。"AI 排版 + AI 发布"已是社区共识形态，与心流的 AI 管线同频；我们的优势（引擎+校验+发布链路）恰好是这些 MCP 封装普遍缺失的部分。
2. **"复制"与"草稿 API"双出口已是成熟模式**：文颜/花生走复制，md2wechat-lite/TypeZen/壹伴走草稿 API，头部项目两者都做——印证我们双通道架构选型正确。
