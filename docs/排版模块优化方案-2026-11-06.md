## 2. 阶段一：合规修复（P0，1 天）

> 全部是"死规则"，改完即可减少一类"发出去才丢格式"的反馈。依据：官方《编辑器插件开发规范》+ draft/add 文档（2026-07 更新）。

### 2.1 digest 上限对齐（UI 已是 120，改的是校验器不一致）
- **审核修正**：`PublishingPage.tsx:174` 的输入框 `maxLength` **已经是 120**——现状是"UI 120 / 校验器 128"的不一致，而不是双重缺口。改一处即可。
- **改哪**：`layout-validator.ts:17`（注释）、`:151-153`（阈值与文案）
- **验收**：`tests/layout-validator.test.ts` 补用例：摘要 121 字报"超出上限 120 字"，120 字通过。
- **顺带小优化（可选）**：发布页摘要留空时提示"微信将自动抓取正文前 54 字作为摘要"（官方默认行为，帮用户做决定）。

### 2.2 font-family 策略：正文跟随微信默认栈
- **问题**：官方明文"不建议设置任何 font-family"（iOS 17+ 字号/字距渲染差异）；当前 `layout-themes.ts` 的 FONT_STACK 铺在 body/h2/h3，SERIF_STACK 铺在 blockquote，`LayoutStyleConfig.bodyFontFamily: 'system' | 'serif'` 也会注入字体。
- **改哪**：
  - `layout-themes.ts:54-57`：`.mly-body/.mly-title/h2/h3` 移除 `font-family` 声明（字号、字重、颜色承担层级）
  - `:187`：blockquote 移除 SERIF_STACK
  - `LayoutStyleConfig.bodyFontFamily`：`'system'` 不再输出 font-family；`'serif'` 保留输出但 UI 标注"实验性：可能与微信真机有差异"
  - 代码块 `'SF Mono', Consolas…monospace` **保留**（业界通行，单行内风险可控）
- **验收**：juice 产物正文节点 style 中无 font-family；预览与微信草稿箱肉眼对比无层级损失。

### 2.3 代码块缩进保全（微信会合并连续空格）
- **改哪**：`article-layout-service.ts` fence 渲染（约 :70-81），逐行 `<p>` 输出前把行首空格替换为 `\u00A0`（不可断空格，微信不合并）：
  ```ts
  line.replace(/^ +/, (m) => '\u00A0'.repeat(m.length)).replace(/ {2}/g, ' \u00A0')
  ```
- **验收**：带缩进的 Python/JSON 代码块粘贴到公众号编辑器后缩进保持。

### 2.4 img 补 `data-w`（官方宽度检测建议，防止误报/溢出）
- **改哪**：`wechat-publish-service.ts` prepareInlineImages 上传图片处。零新依赖：Electron `nativeImage.createFromPath(file).getSize()` 拿原始像素宽，写进 `<img data-w="1024" style="width:100%">`（上传前本地文件可读；外链导入图若拿不到尺寸则不加，不阻塞）。
- **验收**：导出 HTML 中所有本地图 img 带 data-w。

### 2.5 校验器补 6 类规则（对齐官方结构规范）
- **改哪**：`layout-validator.ts` 新增断言（沿用现有 LayoutViolation 结构）
- **审核补充——技术路线**：规则 1/2 是**结构化检查，纯正则做不了，需要 DOM 解析**。好消息：cheerio 1.2.0 已作为 juice 的直接依赖装在 node_modules（已核验 `juice/package.json`）。做法：把 cheerio 提升为 package.json 显式依赖（版本不变、**零新增下载**），结构检查基于它写；不要引入 jsdom（过重）。
  1. **嵌套深度**：同名+同样式+单子节点连续链 > 10 层 → error（官方会自动精简导致样式丢失）
  2. **span[leaf] 禁包块级**：leaf 内出现 section/p/div → error（官方"会被编辑器自动删除"级）
  3. **line-height < font-size** → error（移动端叠字；豁免纯图片节点）
  4. `text-align:start|end` → error；`height:0` 且含文字 → error
  5. `!important` 从 warn 升 **error**（官方"任何场景不建议"，破坏暗黑转换）
  6. **审核新增**：`<a href="#…">` 页内锚点 → warn（微信剥离 id 后锚点必然失效；`renderWechatMarkdown` 只转外链，内部锚点会保留成死链。同时把"目录组件禁止锚点"写进组件规范，防止未来把纯文本目录"优化"成锚点目录）
- **验收**：6 个违规样例 + 1 个合规样例，直接补进**既有的** `tests/layout-validator.test.ts`（vitest，随 `npm test` 跑，CI 已覆盖——不另写独立脚本）。

## 3. 阶段二：预览保真（1~1.5 天）

> 现状：预览 iframe 只有 `body{margin:0}` 重置（`preview-document.ts:5`），与微信真机环境差两层：微信基础样式 + 暗黑模式。这是"预览好看 ≠ 发出去好看"的最大来源。

### 3.1 注入微信基础样式模拟
- **改哪**：`renderer/src/components/layout/preview-document.ts`
- **做法**：把正文包进 `<div id="js_content">`，注入模拟样式（从真实公众号文章 CSS 提取的基线，值可再用样本库校准）：
  ```css
  #js_content { font-size: 17px; line-height: 1.75; letter-spacing: 0.5px; color: #333; }
  #js_content p { margin: 0 0 1em; }   /* UA 默认边距，暴露"没写全重置"的排版稿 */
  #js_content section { margin: 0; }
  ```
- **价值**：排版稿里漏写的 margin/font-size 会**立刻在预览里显形**（预览越真，遗漏越早暴露），主题 CSS 的逐元素重置从此有对照。
- **验收**：同一排版稿，预览截图与公众号草稿箱手机预览并排对比，字号/边距肉眼一致。

### 3.2 暗色预览切换
- **改哪**：同文件 + `LayoutsPage.tsx` 工具栏加"明/暗"切换
- **做法**：暗色时 body 背景 `#191919`（官方暗色正文底色），并给预览容器加一个近似的反色滤镜说明条："暗色为近似模拟，微信以算法转换为准"。同时阶段一 2.5 的校验保证我们不产 `!important`/渐变文字背景，暗色下不会大面积翻车。
- **验收**：5 套主题在暗色预览下文字可读（对比度抽查）。

### 3.3 草稿箱直达动线
- **改哪**：发布结果页（已有 resolveUnknown 人工核对状态机）
- **做法**：推送成功后主 CTA 提供"打开公众号后台核对"→ `shell.openExternal('https://mp.weixin.qq.com/')`；把"已人工核对"入口放在同一屏，缩短"推送 → 打开后台 → 回来点确认"三步。
- **验收**：推送完成后 2 次点击完成核对闭环。

## 4. 阶段三：主题与组件体系升级（3~5 天，可拆两批）

> 目标：适用性更强——让"5 套主题 + 手调参数"升级为"按文体一键装配 + 可分享的定制主题"。

### 4.1 主题 L2：tokens + 配方（批 A，2 天）
- **改哪**：`layout-themes.ts` + contracts
- **结构**：
  ```ts
  interface LayoutThemeDef {
    meta: LayoutThemeInfo           // 已有，保留
    tokens: { accent: string; text: string; muted: string; bg: string; radius: string }
    elements: { h2: string; h3: string; p: string; quote: string; li: string; table: string; divider: string }  // 元素级配方，显式含 margin/padding 重置
    // components 配方挂在现有 layout-components.ts 的变体上
  }
  ```
- **迁移策略**：现有 5 套主题的 CSS 拆解为 tokens+elements 生成（CSS 字符串仍可整体缓存，渲染入口不变，风险低）；`LayoutStyleConfig` 保持为"用户微调层"叠在主题之上（现有语义不变）。
- **约束进 lint**（写进阶段一 2.5 校验器）：元素配方必须含 margin/padding 重置；只允许白名单属性。
- **验收**：5 套主题渲染产物 diff 为零——**固化为 golden file**：把迁移前的产物快照存进 `tests/fixtures/layout-golden/`，在 `tests/layout-e2e.test.ts` 里断言迁移后逐字节一致（自动跑、防回归，不靠人工对比）；且新主题只需写 tokens 即可产出。

### 4.2 新组件（批 A，1 天）
- 章节自动编号：`[[secnum]]` 开关或主题级配置（教程/分析文体刚需）
- 金句卡：`::: hero`（居中强调、大字号、主色锚点——呼应"主色 ≤5 处"规范）
- 提示块扩展：`::: ok`（成功/结论，与现有 tip/warn/key/note 同构，CALLOUT_LABELS 加一项即可）
- **验收**：新组件在 5 套主题下各渲染一次 + 校验器全绿。

### 4.3 主题导入导出（批 B，1 天）
- **做法**：主题 JSON = `LayoutThemeInfo + tokens + 组件变体选择 + LayoutStyleConfig`，用项目已有的 **zod** 定义 schema 校验导入；导出入口放排版工作台。
- **价值**：对齐社区实践（wxeditor/文颜的主题分享形态），用户可自建/交换主题；后续 AI 生成主题也走同一 schema。
- **验收**：导出→改名主色→导入→新主题出现在选择列表且可渲染。

### 4.4 一键排版预设（批 B，1 天，便捷性核心）
- **做法**：预设 = `文体 genre → 主题 + 组件配方 + StyleConfig` 映射表（元信息 suitedFor 已存在，补"推荐组件/推荐 StyleConfig"字段）：
  - 用户点"按文体排版"→ 选"教程 / 深度分析 / 叙事…"→ 自动装配（主题、引言卡、目录、章节编号、数值表对齐…）
  - 记忆用户上次覆盖选择（per-account 存 accountLayout.styleConfig，机制已有）
- **验收**：同一篇文章三种文体预设产出三种版式，且都能过校验器。

## 5. 阶段四：质量闭环（1.5~2 天）

> 校验器只能查"写法"，查不了"实际渲染"。官方 verify-article-structure-spec（MIT）的思路是真实浏览器检测——我们用 Electron 自带 webContents 自研两项最关键的，不引 puppeteer。

### 5.1 渲染级检测（自研，~200 行）
- **做法**：主进程隐藏 `BrowserWindow`（375px，加载排版稿）执行测量脚本：
  1. **溢出**：`scrollWidth > clientWidth` 且非 overflow-x:auto 容器 → error
  2. **叠字**：相邻行盒高度 < fontSize → error（对应官方 line-height 规则的真实渲染版）
- **审核补充——实现约束**：测量窗口必须**单例复用**（模块级懒创建，测量完不销毁、复用加载下一篇），否则每篇排版稿起一个 Chromium 进程，连续排版会吃光内存；且只挂在"推送草稿箱前"与"手动校验"两个时机，不挂在每次预览。
- **接入点**：与 validateWechatLayout 并联，违规直接进现有 LayoutViolation 列表展示。
- **验收**：构造固定宽 500px 的样稿被拦下；连续校验 10 篇稿子进程数不增长（任务管理器/`process.getChildProcessIds` 观察）。

### 5.2 开发期接官方 CLI（不进安装包）
- **做法**：devDependency 加 `verify-article-structure`，新增 `scripts/check-layout.mjs`：对 `tests/fixtures` 里的排版样稿跑 `npm run check --json`，新增违规即退出非零。
- **审核修正——CI 挂点**：项目已有 `.github/workflows/verify.yml`（npm test + build + smoke-workflow + smoke-publishing），把本脚本追加为其中一个 step 即可，不另建 workflow。注意 runner 是 windows-latest，官方 CLI 的 puppeteer 首装要下 Chromium——CI 里用 `PUPPETEER_SKIP_DOWNLOAD` + `PUPPETEER_EXECUTABLE_PATH` 指向 Electron 自带/系统浏览器的方案在 Windows runner 上不稳，**建议先在本地/pre-release 手动跑，验证稳定性后再进 CI**（降级路径：仅本地脚本，不进 CI）。
- **验收**：本地对 fixtures 跑通并输出官方规则编号；进 CI 后违规样例红灯。

### 5.3 真实样本回归库
- **做法**：用 [wechat-article-exporter](https://github.com/wechat-article/wechat-article-exporter) 导出 3~5 篇标杆排版账号的**原始 HTML** 进 `tests/fixtures/wechat-samples/`，写一个对比脚本统计特征（标签分布、内联覆盖率、嵌套深度分布），作为"我们 vs 实战"的量化基线，并校准 3.1 的模拟样式值。
- **验收**：`npm run compare-samples` 输出基线报告；每季度可重跑。

## 6. 阶段五：便捷与增值（2~3 天，可按需拆）

### 6.1 动线收敛（半天）
- 排版工作台：默认勾选品牌头尾（账号级已存配置）、最近使用主题置顶
- 文章详情 → "排版"按钮直达（当前从列表多跳一层则收敛）
- 复制成功 toast 附"打开公众号后台"快捷链接（与 3.3 共用）

### 6.2 长图导出（1 天，渠道增值）
- **审核修正——技术路线**：`capturePage()` 是 BrowserWindow/webContents 的主进程 API，渲染进程的预览 iframe 调不到，且它默认只截可视区域。正确路线：
  1. 主进程开**离屏** `BrowserWindow`（`show:false`，宽 375px，加载排版稿 HTML）
  2. `executeJavaScript` 量出 `document.body.scrollHeight`
  3. `win.setContentSize(375, height)` 等 `did-finish-load` + 一帧 `paint` 事件
  4. `win.webContents.capturePage()` 得整页 PNG → 复用 5.1 的单例窗口，不做第二个隐藏窗口
  - Windows 高 DPI 缩放下截图尺寸 = 逻辑尺寸 × scale，导出时按 `display-loader` 拿到的 scaleFactor 还原逻辑尺寸，避免 125%/150% 缩放的用户导出异常大图
- 适用于 `LayoutPlatform` 已预留的 `xiaohongshu` / `web` 渠道（小红书只有图片流，长图即排版产物）。
- **参考**：文颜的"导出长图"（Apache-2.0，可借鉴交互形态）。
- **验收**：同一篇文章导出长图，字号/间距与预览一致；100%/150% DPI 下导出尺寸一致；超长文（>30000px，部分平台限制）提示分段导出。

### 6.3 小绿书（图片消息草稿，1 天）
- **做法**：`draft/add` 支持 `article_type=newspic`（官方文档已确认：image_info.image_list 永久 MediaID，≤20 张，首张即封面）；复用现有 uploadAsset 通道，把配图工作台的多图直接推成小绿书草稿。参考 md2wechat-lite 的 newspic-draft 命令形态（MIT）。
- **验收**：3~10 张图推送成功且公众号后台显示为图片消息。

### 6.4 远期池（不在本方案排期）
- KaTeX 公式（教研类刚需，参考 doocs/md）
- SVG 互动组件（官方规则齐备但工程量大，差异化亮点）
- 多平台 adaptor（bm.md 的 rehype-adaptor 模式，知乎/掘金）
- MCP 化排版能力（社区趋势，wenyan-mcp 形态）

## 7. 风险与注意事项

| 风险 | 对策 |
| --- | --- |
| 去 font-family 后主题观感变化 | 阶段一 2.2 验收含新旧对比；层级由字号/字重承担，实测微信端反而更一致 |
| 微信规则持续漂移 | 官方规范以 GitHub Issue 驱动迭代——订阅 wechatjs 仓库 release；每次微信更新后重跑 5.3 样本回归 |
