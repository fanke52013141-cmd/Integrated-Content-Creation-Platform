# 实时预览优化方案

> 提出时间：2026-10-05
> 背景：用户提出「边写边看排版效果 / 换主题实时对比 / 手机尺寸真实预览」三项需求
> 结论：**修正此前的判断——实时预览值得做，且当前架构已具备八成条件**

---

## 一、先纠正我之前的错误判断

我在优化方案里写过「P5 排版实时预览 —— 建议不做」，理由是「成本高、非差异化、已有替代」。**这个判断当时成立，现在不成立了。**

| 我当时的理由 | 为什么现在不成立 |
| --- | --- |
| 「用户已有 Typora/Obsidian 写 Markdown」 | 我们的用户不是「用 Obsidian 写完再导出」，而是在我们工具里从选题走到发布。**写作和排版在同一个工作流里**，预览是这条链路的自然一环 |
| 「排版稿已存库，反复生成不同主题对比即可」 | 生成一次要跑完整管线（markdown-it + juice 内联），**不是即时的**。用户改一个字就得重新生成，交互是断裂的 |
| 「预览能展示的东西有限」 | P0–P4 刚做完：6类组件、5 套主题、合规校验。**可预览的内容比之前丰富得多**，预览的价值随之上升 |

更关键的是：**P0–P4 的工作恰好让预览变得廉价了。** 排版管线已经是纯函数 `renderLayoutMarkdown(markdown, platform, themeId)`，在渲染进程里再调一次就能出结果，不需要落库。

这一条是判断转折点：**预览需要的不是新建渲染能力，而是把已有的渲染能力搬到前端、调快它。**

---

## 二、现状盘点（这决定了方案有多便宜）

已有资产比预期多：

| 资产 | 位置 | 对预览的价值 |
| --- | --- | --- |
| `renderLayoutMarkdown()` 纯函数 | `article-layout-service.ts` | **核心**：直接复用，无需重写渲染逻辑 |
| 「预览 / 源码编辑」双模式 | `ArticlesPage.tsx` 的 `editorMode` | 已有切换骨架，只需从「二选一」改成「并排」 |
| 主题 CSS + 组件 CSS | `layout-themes.ts` | 预览与实际排版**同一套样式**，所见即所得 |
| 6 类版式组件 | `layout-components.ts` | 预览里能直接看到组件效果 |
| 合规校验器 | `layout-validator.ts` | **预览时就能提示「这个写法发出去会丢格式」**，这是预览独有的高价值能力 |
| 排版稿存库 | `article_layouts` 表 | 已生成的排版稿可直接调出预览 |

唯一缺的是：**渲染能力在主进程，预览需要在前端即时调用**。

---

## 三、技术方案：把渲染搬到渲染进程

### 核心思路

`renderLayoutMarkdown` 依赖 `juice`（CSS 内联）。这个库**必须在 Node 环境跑**，不能直接进浏览器。

三种做法：

| 方案 | 做法 | 代价 | 评价 |
| --- | --- | --- | --- |
| **A. 主进程 IPC 渲染** | 前端把markdown 发给主进程，调`renderLayoutMarkdown`，拿回 HTML | 每次输入一次 IPC。需防抖（建议 300ms） | ✅ **推荐**。零新依赖，样式与真实排版 100% 一致 |
| B. 渲染进程内联 juice | 把 juice 及其依赖打进渲染包 | 打包体积增加，且 juice 依赖 Node API | ❌ 收益相同、风险更高 |
| C. 前端复刻一套渲染 | 另写一份 | **两份实现必然漂移**，预览与实际不一致 | ❌ 不可接受 |

**选 A**。理由：预览最重要的是「所见即所得」，而复刻渲染必然导致预览和实际发出去的不一样——那这个预览反而有害。

### 交互设计

```
┌─��────────────────┬─────────────────────┐
│  源码编辑│  微信排版预览      │
│                  │                     │
│  textarea        │  [手机] [平板] 宽度  │
│  （现有）│  375×667  约束显示  │
│                  │                     │
│                  │  ⚠️ 合规提示 1 条      │
│                  │  （来自校验器）       │
└──────────────────┴─────────────────────┘
   Ctrl+S 保存
```

**三种预览模式**（用户要的三项）：

| 模式 | 触发 | 实现 |
| --- | --- | --- |
| **并排** | 写文章时默认 | 左编辑右预览，拖动分隔条可调比例 |
| **主题对比** | 选主题时 | 并排展示 2–3 套主题，同一篇文章横向比较 |
| **手机宽度** | 预览区宽度选择器 | 容器 `max-width: 375px` 模拟真机 |

**为什么手机宽度能逼近真机**：微信公众号正文渲染的就是我们输出的内联 HTML，宽度约束是主要变量。**但必须诚实标注**：字号、line-height 完全一致，微信客户端的渲染引擎仍有细微差异（这在调研报告里已记录——粘贴进编辑器后样式保真是需要外部联调验证的环节）。

## 四、开源项目调研结论

我核验了几个候选，**结论是：没有可直接抄的，但有两个值得借鉴的设计**。

### 核验结果

| 项目 | License | 能抄什么 | 结论 |
| --- | --- | --- | --- |
| `AdiRishi/render-md` | 有 LICENSE（未确认类型） | 双向滚动同步、Web Worker 渲染 | ❌ 它做的是「编辑 Markdown 时的实时渲染」，**不是「换主题时的排版效果预览」**，解决的是不同问题 |
| `sszgr/md2wechat` | 有 LICENSE | 手机/桌面预览切换、主题收藏置顶 | ⚠️ 思路可借鉴，但它是纯前端工具、无 API 发布链路 |
| `gzh-design-skill` | **AGPL-3.0** | 「选主题→看长图预览」的产品形态 | ❌ 代码不可用（衍生品必须开源），但**产品形态可借鉴** |
| `CodeMirror 6` | MIT | 编辑器内核 | ⚠️ 见下|

### 一个重要的发现

调研中所有「实时预览」项目（render-md、markdown-live-preview、AtomicMarkDown）用的都是 **CodeMirror 或 Monaco**，没有一个是原生 textarea。

**但我不建议我们换。** 原因：

| 论据 | 说明 |
| --- | --- |
| 我们已有 `editorMode` 骨架与保存逻辑 | 换编辑器要重写光标管理、撤销栈、快捷键、大文本性能 |
| 我们的文章是 AI 生成的 | 多数时候不需要「逐字符编辑」，而是「整体改写 + AI 改稿」 |
| textarea 换编辑器是独立项目 | 与「预览」这个需求无关，会把战线拉长 |

**先用 textarea + 并排布局验证需求是否成立。** 如果验证后确实需要行号/语法高亮/多光标，再评估换CodeMirror（它是渐进式替换，不影响其他部分）。

## 五、实施计划

### 阶段 1：并排预览（1.5 天）—— 验证核心需求

| 任务 | 内容 |
| --- | --- |
| 渲染前置到主进程 IPC | 暴露 `layouts:renderPreview`，调 `renderLayoutMarkdown` |
| 前端防抖 | 300ms（避免每个字符都触发 IPC） |
| 并排布局 | 文章页源码模式改双栏，中间可拖动分隔条 |
| 手机宽度切换 | 375 / 414 / 768 三档 |

**验收**：输入 1000 字文章，300ms 内出预览；切换主题预览立即变化。

### 阶段 2：合规提示内联（0.5 天）—— 预览的差异化价值

在预览区顶部显示校验结果：

```
⚠️ 有 1 处格式会在公众号丢失：<pre> 不被微信支持
   已自动转为 section 结构 [查看]
```

**这是实时预览独有的价值**——不预览就看不到，一预览就知道。这个能力调研的四个项目都没有（它们不面向公众号）。

### 阶段 3：主题对比（1 天）

选主题时并排展示 2–3 套，让用户直接看同一篇文章在不同主题下的样子。

这解决的是 P3 遗留的问题：现在虽然能按文章类型推荐主题，但**用户还是看不到效果就选了**。

### 阶段 4（可选）：换 CodeMirror 6

仅当阶段 1–3 验证后确认需要行号/语法高亮时再做。MIT 许可，可放心使用。

## 六、成本对比

| 方案 | 增量成本 | 价值 |
| --- | --- | --- |
| **阶段 1–3（本方案）** | 约 3 天 | 覆盖用户三项需求，且有校验提示这个独有优势 |
| 换 CodeMirror + Monaco | 额外 3–5 天 | 编辑体验提升，但对 AI 生成为主的场景收益有限 |
| 引入 sharp 做公式转图片 | +30–50MB 包体 | 已决定暂不做 |

**结论：阶段 1–3 是低投入高感知的工作，优先级应高于 P3 的「配方表」等延后项。**

## 七、需要确认的两点

1. **预览是否需要「所见即所得的可编辑」**（在预览区直接改文字）。
   我倾向**不需要**——第 314 行的注释说得对，contentEditable 的 markdown↔HTML 往返会静默丢格式，调研确认这一点。预览应保持只读，编辑走源码区。

2. **手机宽度预览要不要模拟微信客户端的样式差异**。
   我的判断是**不做**——我们无法在应用内准确模拟微信渲染引擎的细微行为，假装能模拟反而误导用户。诚实地标"宽度一致、渲染引擎有差异"更可靠。
