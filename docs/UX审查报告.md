## 一、结论先行

### 总体判断

这是一份**工程实现质量明显高于交互设计成熟度**的代码库。底层架构（安全存储、任务台账、版本管理、真实进度而非假进度）做得相当扎实，几处细节甚至超出同类工具水平。但**导航信息架构存在结构性混乱**，会让用户在第一次使用时就在"该点哪里"上反复试探。

最需要警惕的一点：**代码里的注释和直觉容易让人以为导航已经理顺了，实际上三套导航结构互相矛盾。** 这不是审美问题，是用户会真实迷路的问题。

### 三句话总结

1. **做得对的地方值得保留并推广** —— 空状态的"原因 + 下一步"范式、拒绝假进度、任务台账留痕，这些都做对了。
2. **最严重的问题是导航矛盾**（Warning→P0），不是配色或间距。
3. **对比度问题只需改 3 个令牌值即可消掉 255 处告警的绝大部分**（Warning→P0，性价比最高）。

### 问题分布与处理状态

| 级别 | 数量 | 处理状态 |
| --- | --- | --- |
| 🔴 Blocker | 1 | ✅ **已修复**（启动白屏兜底） |
| 🟠 Warning | 5 | ✅ **全部已修复**（对比度、点击目标/字号、**导航矛盾**） |
| 🟡 Suggestion | 6 | ⚠️ 部分完成（空状态引导、标题层级待处理） |

## 二点五、导航统一（已完成）

### 改造前：五处互相冲突的导航定义

| 位置 | 冲突表现 |
| --- | --- |
| `Layout.navGroups` | 「辅助」组把**智能配图排在内容评审之前** |
| `PipelineSteps.PIPELINE_STAGES` | 评审 → 配图（与侧边栏**相反**） |
| `WorkContext.STAGES` | 正文 → 评审 → 配图 → 排版 → 发布 |
| `App.ROUTE_IDS` | 第四份手写路由清单，顺序又是另一套 |
| `useKeyboardShortcuts.NAV_SHORTCUTS` | 数字键映射：6=素材库、7=配图、8=评审（**第三种顺序**） |

用户在不同位置看到**三种互相矛盾的流程顺序**，无法建立稳定心智模型。

### 改造后：单一事实来源

新增 `src/shared/creation-flow.ts`，全项目只有这一处定义流程：

```
CREATION_FLOW（9 阶段，唯一事实来源）
   ├─ PIPELINE_STAGES   → 顶部流水线（inPipeline 过滤）
   ├─ WORKBAR_STAGES    → 作品栏（inWorkBar 过滤）
   ├─ buildSidebarGroups() → 侧边栏分组（按 group 自动分组）
   ├─ ROUTE_LABELS/GROUPS → 面包屑
   ├─ ALL_ROUTE_IDS     → 路由合法性校验（替代手写清单）
   └─ 数字键映射 + 快捷键面板说明 → 自动派生
```

**顺序（现已全局唯一）**：
账号定位 → 热点洞察 → 选题生成 → 内容框架 → 文章创作 → 内容评审 → 智能配图 → 文章排版 → 发布管理

### 两项关键设计决策

1. **取消「辅助」组**
   评审/配图/排版本就是创作必经步骤，归入「辅助」会暗示"可选"。现已并入「创作」组。

2. **素材库独立为「资源」区**
   它是选题与框架的**输入来源**，不是创作阶段。放在流水线里会让人误以为要走完九步才能写文章。
   现在侧边栏底部用分隔线单独分区，不干扰主链路认知。

### 顺带修掉的两个漏改

- **账号定位页、热点洞察页没接 `PageHeader`** → 顶部缺流程条、页头结构与其余页不一致。已统一。
- **热点/选题/框架三页缺空状态说明** → 走查发现它们只有一句标题，无「为什么空 + 下一步」。已补齐说明文案与引导按钮（如选题页「还没有选题草稿」+「从热点找选题」）。

### 之前 Playwright 跑不起来的真正原因（已定位）

**不是代码问题，是环境变量**：

```bash
ELECTRON_RUN_AS_NODE=1   # ← WorkBuddy 沙盒注入
```

该变量让 Electron 以**纯 Node 模式**启动，因此 `import { BrowserWindow } from 'electron'` 报
`does not provide an export named 'BrowserWindow'`。

**解法**（已写入 `verify-electron.mjs`）：
```js
delete env.ELECTRON_RUN_AS_NODE
args: ['--disable-gpu', '--disable-software-rasterizer', '--no-sandbox']
```
另外无 GPU 环境还需 `--disable-gpu`，否则渲染进程会因 `GPU process isn't usable` 反复崩溃。

| `[Redis] connection failed / max retries` | DailyHotApi 的可选缓存层 | 热点源仍能正常返回，暂不影响；长期可考虑关闭 Redis 依赖 |

## 三、问题清单（按优先级）

### 🔴 P0-1 · Blocker：加载失败时白屏，用户完全无从下手

**位置**：`out/renderer/index.html` → `main.tsx`

**现象**：我在浏览器模式走查时触发了一次真实的加载失败（ES module 被 CORS 拦截），结果是**纯白屏 + 无任何文字**。实测输出：

```
root存在: true
root子节点: 0
body文本长度: 0
控制台: Access to script ... blocked by CORS policy
```

**用户场景**：应用启动失败、资源加载失败、或将来打包配置出错时，用户看到一片空白。没有错误信息、没有重试按钮、无法判断"是没反应还是已经崩了"。

**影响**：用户唯一合理的动作是重启应用，如果重启三次都失败，大概率直接判定"这软件坏了"并卸载。

**推荐改法**：`index.html` 里加一个**不依赖 JS 的静态兜底**，并让 `main.tsx` 捕获启动异常。

```html
<!-- index.html：<div id="root"> 之后 -->
<div id="boot-fallback" style="position:fixed;inset:0;display:none;
     place-items:center;font-family:system-ui;background:#f5f5f7">
  <div style="text-align:center">
    <p style="font-size:15px;color:#1d1d1f">界面没有正常加载</p>
    <p style="font-size:13px;color:#56565c;margin-top:6px">
      可能是资源读取失败，请重新启动应用。</p>
    <button onclick="location.reload()"
      style="margin-top:14px;padding:7px 16px;border-radius:10px;
             border:0;background:#1d1d1f;color:#fff;font-size:13px;cursor:pointer">
      重新加载
    </button>
  </div>
</div>
<script>
  // 6 秒仍未挂载应用 → 判定启动失败
  setTimeout(() => {
    if (!document.querySelector('#root > *')) {
      const el = document.getElementById('boot-fallback')
      if (el) el.style.display = 'grid'
    }
  }, 6000)
</script>
```

同时给 `main.tsx` 加顶层 try/catch，渲染错误态而非空白。

**优先级**：Blocker —— 唯一的"完全不可用"场景。

### 🟠 P0-2 · Warning：导航信息架构自相矛盾（最高优先级）

这是我评审中发现的**最影响真实使用**的问题。项目里同时存在**三套导航结构**，它们互相冲突。

#### 证据：三套结构对照

| 结构 | 定义位置 | 顺序 |
| --- | --- | --- |
| **① 侧边栏分组** | `Layout.tsx:56-91` | 总览 │ 准备(账号定位·热点洞察) │ 创作(选题生成·内容框架·文章创作) │ **辅助(素材库·智能配图·内容评审·文章排版)** │ 发布(发布管理) |
| **② 顶部流水线** | `PipelineSteps.tsx:5-15` | 账号 → 热点 → 选题 → 框架 → 文章 → **评审 → 配图 → 排版** → 发布 |
| **③ 作品栏阶段** | `WorkContext.tsx:12-18` | 正文 → 评审 → 配图 → 排版 → 发布 |

**矛盾点**：

- ①把「智能配图」排在「内容评审」**之前**；②③都把「评审」排在「配图」**之前**。同一个用户在侧边栏和页面顶部看到的先后顺序是**相反的**。
- ①把「智能配图 / 内容评审 / 文章排版」归为「**辅助**」，而「素材库」也混在其中；但流水线里它们是创作主链路。归类暗示"可选"，实际是必经步骤。
- ①把「素材库」夹在「智能配图」之前，但流水线**完全没有素材库**——而素材是选题和框架的输入，属于链路前端。

**用户场景**：一个从「账号定位」开始的新用户，按顶部流水线一步步走（账号→热点→选题→框架→文章→评审→配图→排版→发布），中途想查一下素材，侧边栏却告诉他"素材库"在「辅助」组里，和「智能配图」并列。**他无法建立稳定的心智模型**，只能每次靠试。

**影响**：认知负荷显著升高；新人上手路径不清晰；这是「一致 > 漂亮」原则下最典型的体验债。

**推荐改法**（三选一，建议选方案 A）：

**方案 A · 单一事实来源（推荐）**
把流水线定义抽成唯一常量，侧边栏、流水线、作品栏全部由它派生：

```ts
// src/shared/creation-flow.ts —— 唯一事实来源
export const CREATION_FLOW = [
  { id: 'accounts',    label: '账号定位', group: '准备' },
  { id: 'hotspots',    label: '热点洞察', group: '准备' },
  { id: 'topics',      label: '选题生成', group: '创作' },
  { id: 'frameworks',  label: '内容框架', group: '创作' },
  { id: 'articles',    label: '文章创作', group: '创作' },
  { id: 'reviews',     label: '内容评审', group: '创作' },  // 原「辅助」→ 创作
  { id: 'visuals',     label: '智能配图', group: '创作' },
  { id: 'layouts',     label: '文章排版', group: '创作' },
  { id: 'publishing',  label: '发布管理', group: '发布' }
] as const
```

侧边栏按 `group` 自动分组渲染，顺序与流水线严格一致。**「辅助」组整体取消**——素材库不属于创作阶段，应移至独立的「资源」区（侧栏底部），与创作链路解耦。

**方案 B · 弱化侧边栏分组**
侧边栏取消分组标题，只保留扁平列表 + 分隔线，彻底消除"分类暗示"。

**方案 C · 统一到作品栏**
只在「有当前作品」时显示阶段切换（现有 WorkBar），页面顶部不再重复显示流水线。

**验收标准**：打开任意两个页面，侧边栏顺序、顶部流水线顺序、作品栏阶段顺序三者完全一致。

### 🟠 P0-3 · Warning：对比度不达标 255 处（根因是 3 个令牌）

量化测量（WCAG 2.1 AA，正文阈值 4.5:1）覆盖 13 页，**255 处不达标**。但这不是 255 个独立问题——根因高度集中。

#### 根因 1：`--text-tertiary` 被用了 141 次，对比度仅 3.62:1

```
--text-tertiary #86868b  →  页面底 3.33:1 ✗   白卡 3.62:1 ✗
--text-soft     #aeaeb2  →  页面底 2.03:1 ✗   白卡 2.21:1 ✗   ← 最差
--text-secondary #56565c →  页面底 6.69:1 ✓   白卡 7.29:1 ✓
```

`--text-tertiary` 是全项目最高频的次级文字令牌（141 处），包括**页面描述、空状态说明、流水线未激活阶段、表单提示**——全是用户实际要读的内容。

#### 根因 2：状态语义色在浅色模式下几乎不可读（**比文字问题更严重**）

| 令牌 | 现状 | 页面底 | 白卡 | 影响的功能 |
| --- | --- | --- | --- | --- |
| `--warning` #ff9500 | 橙 | **2.02:1** ✗ | 2.20:1 ✗ | 「还没有可发布的排版稿」等**阻塞提示** |
| `--success` #34c759 | 绿 | **2.04:1** ✗ | 2.22:1 ✗ | 「已验证」「已连接」等**成功状态** |
| `--danger` #ff3b30 | 红 | **3.26:1** ✗ | 3.55:1 ✗ | 错误提示 |
| `--primary` #0071e3 | 蓝 | **4.31:1** ✗ | 4.70:1 ✓ | 选中态流水线步骤 |

**这比文字对比度更值得警惕**：状态色承载的是"能不能用""配没配好""成功没成功"这类**决定性信息**。截图里发布页那条 2.08:1 的橙色阻塞提示（「还没有可发布的排版稿」），恰恰是用户此刻最需要看清的一句话。

#### 已验证的修复方案（我实测了所有候选值）

| 令牌 | 改为 | 页面底 | 最差背景 | 结论 |
| --- | --- | --- | --- | --- |
| `--text-tertiary` | `#6e6e73` | 4.66:1 ✓ | 4.54:1 ✓ | **全背景通过**，视觉差异最小 |
| `--text-soft` | `#8e8e93` | 3.32:1 | — | 仅用于大字或装饰，**不改** |
| `--warning` | `#b25000` | 4.77:1 ✓ | 4.51:1 ✓ | **全背景通过** |
| `--success` | `#047857` | 5.04:1 ✓ | 4.76:1 ✓ | **全背景通过** |
| `--danger` | `#c5221a` | 5.33:1 ✓ | 5.03:1 ✓ | **全背景通过** |
| `--primary` | `#0062c4` | 5.44:1 ✓ | 5.14:1 ✓ | **全背景通过** |

**关键洞察：改 6 个令牌值即可消掉 255 处告警的绝大部分**，比逐页改 CSS 成本低两个数量级，且不会引入新的不一致。

**注意事项**：
- 若状态色同时用于**色块/图标**而非文字，需保留一份亮色版 `--warning-solid` 之类，避免图标也变暗。
- 暗色模式实测**全部通过**（`--warning` 13.93:1、`--success` 9.73:1），只改浅色即可。
- 改完务必复跑 `ux-audit-metrics.mjs` 验证。

### 🟠 P0-4 · Warning：23 处点击目标小于 24×24px

WCAG 2.5.8 建议最小 24×24px。实测发现：

| 尺寸 | 元素 | 位置 |
| --- | --- | --- |
| 13×13px | `<input type="checkbox">` | 发布管理「启用通道」 |
| 16×16px | `<input type="checkbox">` | 模型网关 |
| 56.6×**19px** | `.segmented` 内按钮 | 模型网关「模型服务/素材搜索」分段控件 |
| 1126×**21px** | `.text-button` | 「手动填写公众号素材标识 thumbMediaId →」 |

**用户场景**：触控板精度低、桌面环境缩放 125%/150%、或使用大字号模式时，小目标点不中。尤其 19px 高的分段控件是常用交互。

**推荐改法**：
```css
/* 分段控件与文字按钮补足点击区（视觉尺寸不变，命中区扩大） */
.segmented button { position: relative; }
.segmented button::after {
  content: ''; position: absolute;
  inset: 50% 0; transform: translateY(-50%);
  min-height: 24px;            /* 命中区扩到 24px */
}
input[type='checkbox'] { min-width: 16px; min-height: 16px; }
.field input[type='checkbox'],
.publish-enabled input[type='checkbox'] {
  /* 用伪元素扩大命中区，避免改变视觉密度 */
  position: relative;
}
.field input[type='checkbox']::after,
.publish-enabled input[type='checkbox']::after {
  content: ''; position: absolute; inset: -6px;
}
```

### 🟡 P1-1 · Suggestion：空状态覆盖不完整

`EmptyState` 仅在 **4/13** 页使用：`LayoutsPage`、`PublishingPage`、`ReviewsPage`、`VisualsPage`。

未使用的 9 页在数据为空时各写各的，用户会感受到"有的页面告诉我为什么空，有的只是空白"。

**推荐改法**：其余页面的空态统一改用 `EmptyState`，理由和按钮沿用现有范式：
- 账号定位 → 「还没有账号定位」+「创建第一个账号」
- 热点洞察 → 「还没有收藏的热点」
- 选题生成 → 「还没有选题」+「先浏览热点」或「从主题开始」

### 🟡 P1-2 · Suggestion：表单标签与控件间距偏大

模型网关页实测：标签「显示名称」与输入框之间视觉距离偏远，且标签权重（`--text-tertiary` + 12px）弱于输入框（下边框），用户容易误以为输入框属于上一项。

**推荐改法**：

### 🟡 P1-5 · Suggestion：`--text-soft` 语义不清

`--text-soft`（2.03:1）远低于 AA 阈值，却有 8 处引用。它实质上是"装饰性灰"，不是文字色。

**推荐改法**：改名为 `--text-disabled` 或 `--border-subtle` 一类的非文字语义，并限制只能用于分隔线、占位图标等**不承载信息**的地方。

### 过程中发现的三个隐藏问题（已修）

1. **CSS 压缩器丢弃 `small{}` 规则**
   `small { font-size: 12px }` 在构建产物中消失。原因是该规则相对 `html` 基准可被判定冗余。
   修复：改为 `#root small { ... }` 提高特异性，规则正常进入产物。
   *（实测：源文件有规则 ≠ 产物有规则，必须验证构建结果）*

2. **`.provider-tabs` 样式完全缺失**
   模型网关的「模型服务/素材搜索」两个切换按钮，类名在 CSS 中**根本不存在**，渲染为无样式裸按钮（高度仅 19px）。属组件化重构遗留。
   修复：补齐完整样式，与全站 `.segmented` 视觉对齐。

3. **原生控件尺寸不可控**
   `min-width/min-height` 对 `appearance: auto` 的原生 checkbox 无效（实测停在 20px）。必须 `appearance: none` 才能自定尺寸。
   同时发现 `.switch-row input[checkbox]` 硬编码 `16px` 会覆盖全局规则，已同步修正。
